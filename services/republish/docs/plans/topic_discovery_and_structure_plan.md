## 0. 진단 — 재조합이 왜 최신성을 못 만들었나

먼저 지적하신 재조합 문제부터 답합니다. **프롬프트 튜닝 문제가 아니라 입력 부재 문제입니다.**

`generation/title_recombiner.py:26`

```python
DEFAULT_TITLE_PROMPT = (
    "다음 블로그 제목을 SEO에 최적화된 형태로 재조합해주세요.\n"
    "원본 제목: {title}\n\n"
    "규칙:\n"
    "- 원본의 핵심 키워드를 유지\n"
    ...
)
```

**입력이 원본 제목 문자열 하나뿐입니다.** 트렌드 신호도, 최신 자료도, 사람들이 실제로 뭘 묻는지도 들어가지 않습니다. **모델에게 주어진 정보가 원본 제목뿐인데 최신성 있는 제목이 나올 수는 없습니다.** 표현만 바꿀 수 있습니다.

코드 주석이 이미 이 한계를 두 번 인정합니다.

> `# 핵심어를 명시한다. 이게 없으면 재조합이 검색되는 말을 흘린다.`
> `# 실제로 다섯 스타일이 거의 같은 제목으로 수렴했다.`

**재조합은 "변형기"입니다.** 있는 제목의 표현을 바꿉니다. 기대하신 건 "발굴기"였고, 그건 다른 물건입니다.

→ **결론: 재조합을 고치는 게 아니라, 재조합을 거치지 않는 새 경로를 만들어야 합니다.**

## 1. 질문 네 건에 대한 답

### 1-1. 홈피드 트렌드 분석과 지식인 주제 추출을 워크플로우로 옮길 수 있는가

**가능합니다. 그리고 생각보다 훨씬 쉽습니다.**

지금 쓰는 네이버 검색 API는 **엔드포인트만 바꾸면 다른 소스가 열립니다. 인증 키는 그대로입니다.**

```
현재: https://openapi.naver.com/v1/search/webkr.json   ← 웹문서 하나
```

| 엔드포인트 | 용도 |
|---|---|
| `kin.json` | **지식iN** — 수작업으로 하신 그 소스 |
| `cafearticle.json` | 카페 — 실사용 후기·질문 |
| `news.json` | 뉴스 — 최신성 검증용 |
| `encyc.json` | 백과 — 용어·정의 |
| `doc.json` | 전문자료 |

`sort=date` 를 주면 최신순 정렬도 됩니다.

**즉 `kin.json` 하나 붙이면 지식인 워크플로우의 입력이 확보됩니다.** 별도 크롤링도, 화면 제어도 필요 없습니다. `reference_search_service.py`(147줄)에 소스 어댑터를 추가하는 수준입니다.

홈피드 트렌드는 API가 없어 다릅니다. 인기 검색어는 **수집 대상**이지 검색 API가 아니라, 별도 수집 경로가 필요합니다(난이도 중간). 다만 **트렌드는 지식인보다 우선순위가 낮습니다.** 뒤에서 설명합니다.

### 1-2. 인기 검색어를 넣으면 결과가 달라지는가

**재조합을 그대로 두면 별로 안 달라집니다.**

인기 검색어를 어디에 넣느냐가 전부입니다.

| 투입 지점 | 결과 |
|---|---|
| 재조합 단계 | 원본 제목이 여전히 주인공. **키워드 하나 갈아끼운 수준** |
| **주제 발굴 단계** | 주제 자체가 달라짐 |

지금 구조에서 인기 검색어를 재조합에 넣으면 `"지커 코리아 7X"` 같은 단어가 기존 제목에 끼워 넣어질 뿐입니다. **주제는 그대로입니다.**

그래서 제안을 수정합니다. **인기 검색어는 재조합이 아니라 주제 발굴 단계에 들어갑니다.** 그리고 **새 경로는 재조합을 거치지 않습니다.** 재조합은 기존 수집 제목 경로에만 남겨둡니다.

### 1-3. 태그는 애드센스에 효용이 있는가 — 제안을 철회합니다

**지적이 맞습니다. A-3을 기각합니다.**

| 플랫폼 | 태그 효용 |
|---|---|
| 네이버 블로그 | **있음.** 검색 노출에 실제 기여 |
| 워드프레스 | **낮음, 오히려 위험** |
| Blogger | **낮음** |

**워드프레스**: 태그마다 아카이브 페이지가 자동 생성됩니다. 글 하나에 태그 다섯 개면 **본문이 거의 없는 목록 페이지 다섯 장**이 색인 대상이 됩니다. 자동 발행이면 이게 누적돼 **얕은 페이지가 본문 수의 몇 배로 불어납니다.** SEO 플러그인들이 태그 아카이브를 기본 `noindex`로 두는 이유입니다.

**Blogger**: 라벨 페이지도 같고, `?max-results` 같은 파라미터로 중복 URL까지 생깁니다.

**애드센스 관점에서 특히 불리합니다.** 이미 `guntamoney`가 "가치 없는 콘텐츠"로 반려된 이력이 있습니다. 얕은 페이지 양산은 정확히 그 심사에 걸리는 유형입니다.

→ **태그는 네이버를 실제로 하게 될 때만 다시 꺼냅니다.**

### 1-4. A-1이 잘 되면 재검색이 필요 없지 않은가

**정확한 지적이고, 제 설명이 부족했습니다. 순서를 뒤집어 설명하겠습니다.**

재검색은 **목적이 아니라 결과**입니다. 제가 수작업에서 실제로 한 순서는 이렇습니다.

```
1. 질문을 읽고 "이 사람이 진짜 막힌 지점"을 찾는다
2. 그걸 답하려면 무엇을 알아야 하는지 [목록]을 만든다   ← 검색 전
3. 목록의 각 항목을 별도 쿼리로 던진다 (병렬)
4. 결과를 [목록]에 대조한다 — 빈칸이 있나
5. 빈칸이 있으면 그 항목만 다시 검색
6. 채워진 목록으로 구조를 짜고 쓴다
```

**핵심은 2번입니다.** 퇴거 청소 글에서는 이 목록이었습니다.

- 원상회복 의무의 법적 근거는 무엇인가
- 통상손모는 누구 책임인가
- 계약서 특약이 있으면 달라지는가
- 보증금에서 임의 공제됐을 때 밟을 절차는

**이 목록이 있으니 "자료가 충분한가"를 판정할 수 있었습니다.** 목록이 없으면 판정 기준 자체가 없습니다.

말씀하신 **"보이지 않는 부분"이 이 목록입니다.** 블로그 오토에는 이게 없습니다. 제목 하나에서 쿼리 하나를 뽑고 끝이라, 무엇이 채워졌고 무엇이 비었는지 알 방법이 없습니다.

**그래서 답은 이렇습니다.** A-1로 소스를 늘리면 자료의 양과 질이 올라가 재검색 **빈도는 줄어듭니다.** 하지만 **목록 없이는 애초에 재검색을 해야 할지조차 판단할 수 없습니다.** 재검색 루프를 만드는 게 목표가 아니라, **근거 목록을 만드는 게 목표**이고 재검색은 거기 딸려오는 부속입니다.

이 문서에서는 이 목록을 **근거 체크리스트**라고 부르겠습니다.

## 2. 주제 발굴 워크플로우 재설계

### 2-1. 지식인을 왜 쓰는지 — 로직으로 옮기기

말씀하신 통찰이 설계의 출발점입니다.

> "해당 니치를 확장하기 위한 도구로 지식인을 삼은 것입니다. 집단지성의 힘을 빌린 것이죠. 많은 사람들이 각각의 상황에 따라 같은 주제라도 다른 궁금증이 생길 것이고 그것이 글의 주제가 될 수 있다."

실제 결과가 이를 증명합니다. **「이사 견적」이라는 니치 하나에서 11편이 나왔습니다.**

| 글 | 상황 축 |
|---|---|
| 송림동→주안동 | 지역 간 근거리 |
| 15평→32평 | 평수 확대 |
| 사다리차 vs 포장이사 | 운반 방식 |
| 서울→천안 | 장거리 |
| 보관이사 | 일정 공백 |
| 파주→부산 소형 | 장거리 + 소량 |
| 사다리차 비용 | 단가 |
| 원룸 견적 | 최소 규모 |
| 같은 건물 2→3층 | 거리 0 |
| 경유 이사 | 합가 |
| 일반 vs 반포장 | 서비스 범위 |

**키워드로는 이게 나오지 않습니다.** 「이사 견적」에서 "같은 건물 2층에서 3층"은 도출되지 않습니다. **상황은 사람이 만들어냅니다.**

로직으로 옮기면 한 줄입니다.

```
주제 = 니치 × 실제 사람의 구체적 상황
```

니치는 우리가 갖고 있고, **상황은 지식인·카페에 있습니다.**

### 2-2. 새 경로 설계

```
① 니치 (topic/subtopic)
     ↓
② 질문 수집        kin.json + cafearticle.json (sort=date)
     ↓             니치 키워드로 실제 질문을 긁는다
③ 상황 추출        질문에서 [상황 축]을 뽑는다
     ↓             "2층→3층 / 엘베없음 / 장롱3짝" 같은 조건
④ 군집·중복 제거   같은 상황끼리 묶고, 이미 쓴 주제 제외
     ↓             (기존 topic_dedup_gate 재사용)
⑤ 주제 후보 산출   상황 + 니치 → 주제 문장
     ↓             ※ 재조합 안 거침
⑥ 트렌드 가중      인기검색어·뉴스와 겹치면 우선순위 ↑
     ↓
⑦ 최신성 판정      제도 변경·시의성 확인 (news.json)
     ↓
⑧ 제목 생성        상황을 제목에 녹인다
     ↓
⑨ 근거 체크리스트   "이 제목에 답하려면 무엇을 알아야 하나" ★
     ↓
⑩ 항목별 병렬 검색  체크리스트 항목 = 쿼리 1개. 소스는 항목 성격에 따라
     ↓
⑪ 충족 판정        빈칸 확인 → 빈칸만 재검색 (1회 상한)
     ↓
⑫ 구조 설계        체크리스트 순서로 소제목 구성
     ↓
⑬ 본문 생성
     ↓
⑭ 자체 검증        상투어·금지태그·1인칭 빈도
```

**⑨가 이 설계의 중심입니다.** ⑩·⑪·⑫가 전부 ⑨에 의존합니다.

### 2-3. 기존 경로와의 관계

**기존 경로를 없애지 않습니다. 나란히 둡니다.**

| 경로 | 출처 코드 | 재조합 | 용도 |
|---|---|---|---|
| 키워드 → 제목 수집 | `title_collect` | **거침** | 기존 유지 |
| 도메인 일괄 수집 | `domain_extract` | **거침** | 기존 유지 |
| 키워드 AI 생성 | `keyword_module` | 안 거침 | 기존 유지 |
| 뉴스 결합 | `news_gen` | 안 거침 | 기존 유지 |
| **질문 발굴** | `SRC_QUESTION` **신설** | **안 거침** | 니치 확장 |

`title_source.py`에 코드 하나를 추가하는 형태라 기존 화면·필터·통계가 그대로 붙습니다. **출처별 승격률 비교도 자동으로 됩니다.**

### 2-4. 근거 체크리스트 상세

**생성 시점**: 제목 확정 직후, 검색 전

**산출 형태**

```json
{
  "title": "원룸 퇴거 청소비, 내야 할 때와 안 내도 될 때",
  "core_question": "퇴거 청소는 법적 의무인가",
  "checklist": [
    {"id": 1, "ask": "원상회복 의무의 법적 근거", "source": "law", "filled": false},
    {"id": 2, "ask": "통상손모의 책임 주체", "source": "law", "filled": false},
    {"id": 3, "ask": "청소비 특약의 효력 요건", "source": "web|kin", "filled": false},
    {"id": 4, "ask": "보증금 임의공제 대응 절차", "source": "web|news", "filled": false}
  ]
}
```

**`source` 필드가 소스 라우팅을 합니다.** 법령 질문은 법령 소스로, 경험 질문은 지식인·카페로, 시의성 질문은 뉴스로 갑니다. **"검색 기준이 더 디테일하다"고 하신 부분이 이것입니다.**

**충족 판정**: 항목별로 `filled` 를 채웁니다. 미충족 항목만 쿼리를 바꿔 1회 재검색하고, 그래도 안 채워지면 **그 항목을 빼고 진행**합니다(글을 막지 않음).

**구조 설계**: 채워진 항목이 소제목 순서가 됩니다. 항목이 다르면 구조가 다릅니다. 퇴거 청소와 경유 이사의 구조가 달랐던 이유가 여기입니다.

### 2-5. 트렌드의 위치 — 우선순위를 낮춥니다

인기 검색어는 **⑥ 가중치**로만 씁니다. 주제를 만들지 않습니다.

이유가 둘입니다. 첫째, 인기 검색어는 **상황이 없습니다.** `"지커 코리아 7X"` 만으로는 글의 축이 안 나옵니다. 둘째, **경쟁이 가장 심한 구간**이라 신생 블로그가 먹기 어렵습니다.

**지식인 질문은 반대입니다.** 상황이 구체적이고 경쟁이 적습니다. **먼저 할 것은 지식인이고, 트렌드는 나중입니다.**

## 3. 구조 다양화 — 제안하신 4건 검토

네 건 모두 **타당하고 반영합니다.** 코드와 대조한 결과를 붙입니다.

### 3-1. 니치별 프롬프트 모듈 분리 — **데이터 구조는 이미 준비돼 있습니다**

`generation/adsense_niche.py:15`

```python
def resolve_module_niche(module_settings) -> Optional[List[int]]:
    ...
    ids = [int(x) for x in (module_settings.get("niche_topic_ids") or []) ...]
```

**`niche_topic_ids`가 이미 리스트입니다.** 복수 니치를 담을 수 있습니다.

`FlowModule`도 `execution_order`를 갖고 있어 **한 플로우에 모듈을 여럿 매달 수 있습니다.**

**필요한 건 둘뿐입니다.**
1. UI — 블로그 선택 시 니치가 전부 선택되는 동작을 **부분 선택 가능**하게
2. 실행 — 생성 시 제목의 topic_id를 보고 **담당 모듈을 고르는 분기**

난이도: 중간. 마이그레이션 불필요.

### 3-2. 동일 니치 복수 프롬프트 로테이션 — **이게 제 「지면별 프리셋」보다 낫습니다**

지적하신 근거가 정확합니다.

> "한 블로그에서 동일한 구조로 글이 발행되면 검색사이트에서 걸러낼 수 있다고 보았습니다."

제가 앞 보고서에서 제안한 「지면별 프리셋」은 **축이 하나**입니다. 지면이 정해지면 구조도 하나로 고정됩니다. 로테이션은 **같은 축 안에서도 매번 달라집니다.** 이쪽이 맞습니다.

**설계**

```json
"prompt_rotation": {
  "enabled": true,
  "mode": "random | sequential | by_keyword | by_niche",
  "prompt_ids": [12, 15, 19],
  "cursor": 0
}
```

| 모드 | 동작 |
|---|---|
| `random` | 매 글 무작위 |
| `sequential` | 순번대로 (모듈별 커서 저장) |
| `by_keyword` | 키워드 패턴 → 프롬프트 매핑 |
| `by_niche` | 하위 니치 → 프롬프트 매핑 |

**`sequential`은 커서 저장이 필요합니다.** 모듈 settings에 두면 동시 실행 시 경합이 생기니, 기존 `flow_execution_state` 계열에 붙이는 편이 안전합니다.

난이도: 중간.

### 3-3. 애드센스 / CPA 분기 — **기존 스위치를 확장하면 됩니다**

`generation/adsense_prompt_switch.py`에 승인용 프리셋 전환 로직이 이미 있습니다(`APPROVAL_PRESET_KEY`, `find_preset()`). **같은 자리에 목적 축을 하나 더 넣는 형태**입니다.

```
목적: adsense | cpa | info
  ↓
목적별 프롬프트 집합 → 그 안에서 3-2 로테이션
```

말씀대로 **애드센스용과 CPA용은 구조가 다를 수밖에 없습니다.** 수작업 CPA 글은 `쟁점 → 근거 → 판단 기준 → 실행 조언 → CTA` 였고, 정보성 글(장기수선충당금·첫 독립)은 CTA가 아예 없었습니다.

난이도: 낮음.

### 3-4. 템플릿 이미지 복수 — **현재 단수 하드코딩입니다**

`generation/template_image_service.py:221`

```python
raw_path = config.get("template_image")
```

**문자열 하나입니다.** 복수화하려면 이렇게 갑니다.

```json
"template_images": [
  {"path": "blogs/21/template/t1.png", "topic_ids": [24]},
  {"path": "blogs/21/template/t2.png", "topic_ids": [24]},
  {"path": "blogs/21/template/t3.png", "topic_ids": []}
],
"template_image_mode": "random | by_niche | by_keyword | sequential"
```

**하위 호환이 필수입니다.** 블로그 21이 이미 `template_image` 단수로 운영 중이라, `template_images`가 없으면 기존 키를 읽도록 폴백을 둡니다.

난이도: 낮음. 오버레이 설정은 공유하고 배경만 바뀌므로 `overlay_config`의 나머지 필드는 손대지 않습니다.

## 5. 전제와 리스크

**호출 비용.** 체크리스트를 넣으면 글 1편당 AI 호출이 **3회 → 6~8회**가 됩니다. 재검색 상한(1회)과 체크리스트 항목 상한(4~5개)을 **코드에 고정**해야 합니다.

**모델 배분은 실측이 필요합니다.** 체크리스트 생성과 충족 판정은 **판단 작업**이라 가성비 모델이 제대로 못 할 수 있습니다. 반대로 본문 생성은 가성비 모델로도 됩니다. **단계별로 모델을 나누는 편이 유리할 가능성이 크지만, 같은 제목으로 A/B를 돌려 확인해야 합니다.** 넣고 나서 품질이 그대로면 호출만 두 배가 됩니다.

**지식인 수집량.** 네이버 검색 API는 일일 호출 한도가 있습니다. 질문 수집을 매 글마다 하지 말고 **니치별로 주기 수집해 풀에 쌓아두고 꺼내 쓰는 구조**가 맞습니다.

**저작권.** 지식인 질문을 **그대로 인용하지 않습니다.** 상황 축만 뽑아 쓰고 각색합니다. 이번 수작업에서 지킨 방식 그대로입니다.

**중복.** 같은 니치에서 질문을 계속 뽑으면 상황이 겹칩니다. ④ 단계의 중복 제거가 실효를 내야 하고, **이미 발행한 글의 상황 축을 저장해 대조**해야 합니다.
