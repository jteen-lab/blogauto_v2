# 블로그 오토 — 애드센스 승인 지원 기능 작업계획서

> **상태**: 부분 구현 진행 중(F1/F2/F6/F9 최소 구현 완료, F3/F4/F5/F7/F8/F10 미착수) · **작성일**: 2026-08-03 · **최종 갱신**: 2026-08-11 · **작성**: Claude
> **목적**: guntamoney.blogspot.com 애드센스 반려("가치가 별로 없는 콘텐츠") 재분석을 근거로,
> blogauto가 생성·발행하는 블로그의 **애드센스 승인 확률을 높이는 기능**을 설계한다.
> **주의**: 본 문서는 기능 근거·명세 초안이다. 실제 개발은 기능별 Flowchart(`docs/flowcharts/`) 선작성 후 진행한다.

---

## 1. 배경 — 반려 진단 (3개 분석 수렴)

이전 분석(메모리 `project_adsense_rejection`), 외부 AI(체셔캣) 분석, 2026 정책 재검증이 **동일 결론으로 수렴**. 반려 4대 축:

1. **신뢰/정책 페이지 부재** — 개인정보처리방침·이용약관·소개·문의 없음 → "불완전·의심 사이트" 판정.
2. **주제 산포(니치 없음)** — 은행·여행·보험·연금·가전 뒤섞임 → E-E-A-T 축적 불가, content farm 패턴.
3. **대량·고속 자동발행** — 월 최대 158개 → 2026.3 강력 시행된 **scaled content abuse** 타깃.
4. **얕은 정리형·템플릿·중복** — 공공정보 재나열(Information Gain 미달), 600자↓ thin content, 저자·출처·직접경험 전무.

### 2026 정책 핵심(설계 전제)
- **AI 생성 자체는 금지 아님.** "가치·사람 검수·E-E-A-T"를 갖추면 승인 → **자동화를 유지하되 신호를 붙이는 방향**이 유효.
- Information Gain(기존 웹에 없는 새 정보/관점) 요구, Information Redundancy 감점.
- 식별 가능한 저자·검증 가능한 전문성·편집 감독 신호 요구.
- 권장: 고품질 장문 20~30편, 재신청 전 2~3주 대기.

## 2. 목표 / 비목표

**목표**
- blogauto로 만든 블로그가 애드센스 **최소 요건 + 품질 신호**를 자동/반자동으로 충족하도록 지원.
- 발행 전/후 **준비도 진단**으로 재신청 성공률 향상.

**비목표(한계 명시)**
- 승인 **보장 아님**. "검증 가능한 전문성"·"진짜 직접 경험"은 완전 자동화 불가 → blogauto는 **신호·구조·니치·속도 관리**로 확률을 높이는 데 집중.
- 애드센스 계정 신청/심사 자동화는 범위 밖(수동).

## 3. 기능 명세

우선순위: **P1(전제조건, 즉효)** → **P2(근본 품질)** → **P3(사전 진단)**. 각 항목에 애드센스 근거 표기.

### Phase 1 — 자동 생성(전제조건, 쉬움)

**F1. 필수 페이지 4종 자동 생성** `P1` — **완료**(연락 채널은 2026-08-11
`contact_form_url` 옵트인으로 mailto 노출 문제 해결, [[project_contact_form_conversion]])
- **내용**: 개인정보처리방침·이용약관·소개(About)·문의(Contact) 페이지를 블로그별로 생성·메뉴 노출.
- **구현 방향**: 페이지 템플릿(변수: 블로그명·도메인·운영자/연락처·발행주체) + 플랫폼별 발행 —
  - Blogger: Pages API(`pages.insert`)로 정적 페이지 생성.
  - WordPress: REST `wp/v2/pages`로 생성.
  - 생성 후 메뉴/위젯에 링크 노출(플랫폼별).
- **영향 영역**: 블로그 등록/설정, 발행 어댑터(Blogger/WordPress), 템플릿 저장소.
- **근거**: 필수 페이지 부재 = 단독 반려 사유. 가장 확실한 즉효.

**F2. 저자성(E-E-A-T) 신호 주입** `P1` — **완료**(옵트인, author_profile 미설정 블로그는 영향 없음)
- **내용**: (a) 글별 저자 바이라인, (b) 저자 소개 페이지, (c) 푸터 "본 콘텐츠는 사람이 검수·편집합니다" 편집감독 문구.
- **구현 방향**: 블로그별 저자 프로필(이름·소개·전문분야) 설정 필드 추가 → 생성 시 본문/푸터에 주입.
- **영향 영역**: 블로그 설정 모델, 생성 파이프라인(본문 조립/템플릿), 스타일 편집기.
- **근거**: "식별 가능한 저자·편집 감독 신호" 요구.

**F3. 카테고리/내비게이션 메뉴 자동 구성** `P1` — **미착수**(플랫폼별 템플릿 파손 리스크로 보류, `docs/flowcharts/adsense_sprint1_p1.md` 참고)
- **내용**: 주제 카테고리 기반 상단 메뉴/사이드바 구성(월별 아카이브만 있는 현 구조 개선).
- **영향 영역**: 발행 어댑터, 블로그 초기 세팅.

**F10. 문의 폼 자동 생성 기능** `P1` — **미착수**(신규, 2026-08-11 사용자 요청)
- **배경**: F1 완료로 mailto 노출 문제는 `contact_form_url` 옵트인으로 해결했으나,
  현재는 폼 URL을 운영자가 Google Forms/Formspree 등 외부에서 **수동으로 하나씩
  생성**해 블로그 설정에 입력해야 함
  ([[project_contact_form_conversion]] "미해결" 항목의 후속). §10 A/B 테스트처럼
  블로그 8개 이상을 동시 운영할 경우 동일 폼 URL을 재사용하면 "동일 소유주 묶음"
  노출 위험이 커서(§10 주의) 블로그마다 서로 다른 폼이 필요한데, 수동 생성은
  확장성이 없음.
- **목표**: 블로그 등록/설정 시점에 문의 폼을 **자동 생성**하고 그 URL을
  `contact_form_url`에 자동으로 채워 운영자 수작업을 제거하고, 블로그별 폼 분리를
  기본값화한다.
- **검토할 구현 옵션(조사 필요, 우선순위 아님)**:
  1. **Google Forms API(`forms.googleapis.com`) 자동 생성** — `forms.create`로
     이름/이메일/메시지 필드를 가진 문의 폼을 자동 생성 가능. **알려진 한계**:
     API로 생성한 폼에 "응답 시 이메일 알림"을 켜는 공식 엔드포인트가 없음(현재는
     UI 수동 설정 또는 `watches` API의 Pub/Sub 알림만 가능) — 실사용 가능 여부
     조사 필요.
  2. **Formspree API 자동 생성** — 유료 플랜에서 폼을 프로그래매틱하게 생성하는
     API 제공 여부·요금제 확인 필요.
  3. **자체 호스팅 경량 폼 엔드포인트** — blogauto 서버에 블로그별 문의 폼 수신
     엔드포인트(`/contact/{blog_id}`)를 직접 구현, 제출 시 해당 블로그 소유자
     이메일로 전달(SMTP/이메일 발송 연동 필요). 외부 서비스 의존 없이 완전
     자동화 가능하나 스팸 방지(캡차 등)·이메일 발송 인프라 신규 구축 필요.
- **권장 방향(초안)**: 옵션 3(자체 호스팅)이 외부 API 제약(옵션1 알림 한계, 옵션2
  요금제 불확실성)에 걸리지 않고 완전 자동화가 가능해 가장 유력. 스팸 방지
  (rate limit/허니팟)와 발송 인프라(기존 이메일 발송 로직 존재 여부) 조사 후
  착수 여부 결정.
- **구현 방향(자체 호스팅 채택 시)**:
  - 블로그 등록/설정 시 `contact_form_url`을 자동으로 `/contact/{blog_id}` 형태로
    채움(운영자 수동 입력 필드는 override 옵션으로 유지, 기존 하위호환 유지).
  - 신규 라우터: 폼 렌더링 + POST 처리(rate limit/허니팟 필드로 스팸 방지) +
    블로그 소유자 이메일로 전달.
  - `required_pages_templates.py`의 iframe 임베드 대상을 자체 엔드포인트로
    지정할 수 있도록 확장(기존 외부 URL 방식과 공존).
- **영향 영역**: 블로그 등록/설정 API, `required_pages_templates.py`(iframe 대상
  URL 생성 로직), 신규 문의 폼 라우터/서비스, 이메일 발송 연동(신규 또는 기존
  재사용 여부 확인).
- **데이터 변경**: `contact_form_url`이 자동 채움 값(자체 엔드포인트)인지 운영자
  수동 입력값(외부 URL)인지 구분할 플래그가 필요할 수 있음(조사 후 결정).
- **근거**: §10 A/B 테스트에서 8개 블로그 동시 운영 시 서로 다른
  `contact_form_url`이 필요 — 수동 생성이 병목.

### Phase 2 — 콘텐츠 품질/구조(근본 해결, 중간)

**F4. 니치(주제) 강제** `P2` ⭐
- **내용**: 블로그별 **단일 니치**(예: "생활 금융정보")를 지정하고, 지정 니치 밖 주제 생성 시 **차단/경고**.
- **구현 방향**: 블로그 설정에 `niche`/허용 카테고리 범위 필드 → 제목·주제 생성 단계에서 니치 적합성 검사(카테고리 매핑 또는 AI 분류). 이탈 주제는 스킵/보류.
- **영향 영역**: 주제·제목 생성 모듈, 카테고리 분류(기존 재분류 로직 재사용 가능), 블로그 설정.
- **근거**: "broad topics = trap", E-E-A-T 니치 집중. 체셔캣·2026정책 핵심.

**F5. 발행 케이던스 조절** `P2`
- **내용**: 일/월 발행 상한 + **승인 전 저속 모드**(예: 일 1~2편) → scaled content abuse 회피.
- **구현 방향**: 스케줄러/오토런에 블로그별 발행 상한·승인상태 플래그 추가. 승인 전엔 상한 강제.
- **영향 영역**: 스케줄러, 오토런 디스패치, 블로그 설정(`adsense_status`).
- **근거**: 월 158개 = scaled content abuse. 발행속도가 실질 레버.

**F6. 최소 분량·구조 게이트** `P2` — **완료**(글자수 게이트만; 표비율·문단다양성은 미구현)
- **내용**: 600자↓ thin content·과도한 템플릿 반복·표만 있는 글 **발행 차단/보류**.
- **구현 방향**: 발행 직전 검사(글자수·문단수·표비율·문단 다양성). 미달 시 재생성 또는 검수 큐로.
- **영향 영역**: 발행 파이프라인 검증 단계.
- **근거**: thin content = 대표 반려 사유.

**F7. Information Gain 프롬프트 개편** `P2` ⭐
- **내용**: 생성 프롬프트를 "정보 재나열 금지 → 고유 관점·구체 팁·비교·주의점·출처 링크 포함"으로 개편. 출처 자동 인용.
- **구현 방향**: 생성 모듈 프롬프트 템플릿 개정 + 출처 수집/삽입 로직. 섹션 구성을 "무엇을/왜 유용/어떻게(구체)"로.
- **영향 영역**: 생성 프롬프트 템플릿(`prompt-form-*`, 생성 서비스).
- **근거**: Information Gain / Redundancy.

**F8. 발행 전 중복 방지(유사도 게이트 재사용)** `P2`
- **내용**: 발행 직전 기존 글과 **주제 중복** 검사 → 중복이면 차단.
- **구현 방향**: **이번에 구축한 유사도 통합 식별자 게이트**([[project_similarity_unified_gate]] · `docs/flowcharts/unified_discriminator_gate.md`) + 회색지대 AI를 발행 전 검사에 재사용.
- **영향 영역**: 발행 파이프라인, `SimilarityService`/`TokenDFService`.
- **근거**: 중복·유사 콘텐츠 감점. 기존 자산 재활용으로 저비용.

### Phase 3 — 사전 진단(재신청 대비)

**F9. 애드센스 준비도 감사(체크리스트)** `P3` — **최소 구현 완료(2026-08-11)**:
`GET /blogs/{id}/settings/adsense-readiness` + 설정 UI 요약 카드
(`AdsenseReadinessService`). 필수 페이지/저자 프로필/연락 채널(폼 vs
이메일)/발행 20편 이상 4개 항목만 자동 점검 — 아래 나머지 항목(thin
비율·중복 비율·니치·케이던스)은 정량 집계 로직이 없어 미구현, 3.3
수동 체크리스트로 대체. A/B 테스트 버킷(필수페이지·E-E-A-T O/X)
확인 용도로는 충분.
- **내용**: 블로그 스캔 → 항목별 점검·점수·리포트. 재신청 게이트로 활용.
- **점검 항목(초안)**:
  - [ ] 필수 페이지 4종 존재
  - [ ] 저자 정보/바이라인
  - [ ] 단일 니치 집중도(주제 산포도 지표)
  - [ ] 총 글 수 ≥ 20~30
  - [ ] thin(600자↓) 글 비율
  - [ ] 중복/유사 글 비율(F8 게이트)
  - [ ] 출처 포함 글 비율
  - [ ] 발행 케이던스(급증 여부)
  - [ ] 내비게이션/카테고리 메뉴
- **산출**: 점수 + "미충족 항목 → 조치" 리포트.
- **영향 영역**: 신규 감사 서비스 + UI(블로그 카드/상세).

## 4. 예상 데이터/설정 변경

## 5. 성공 기준
- F1~F3 적용 블로그가 준비도 감사 **필수 항목 100%** 통과.
- F4~F8 적용 후 신규 글의 thin/중복/니치이탈 비율 목표치 이하.
- 재신청 블로그 승인률 향상(정성).

## 6. 리스크 / 한계
- **승인 보장 불가** — 진짜 전문성/경험은 자동화 한계. 신호·구조로 확률만 높임.
- 플랫폼 차이(Blogger vs WordPress) — 페이지/메뉴 API 상이, 어댑터별 구현 필요.
- 니치 강제가 기존 대량발행 운영과 충돌 가능 → 승인 전/후 모드 분리로 완화.
- 프롬프트 개편이 생성 품질/속도에 영향 → A/B 검증 필요.

## 7. 단계별 로드맵(제안)
1. **Sprint 1(P1)**: F1 필수페이지 + F2 저자성 + F3 메뉴 + F10 문의 폼 자동 생성
   → 즉효 전제조건. F10은 §10 A/B 테스트를 8개 블로그 이상으로 확장할 때
   병목이 되므로 우선순위 상향 검토.
2. **Sprint 2(P2)**: F4 니치 강제 + F5 케이던스 + F6 분량게이트.
3. **Sprint 3(P2)**: F7 프롬프트 개편 + F8 중복 게이트(기존 유사도 재사용).
4. **Sprint 4(P3)**: F9 준비도 감사 + UI.
> 각 Sprint 착수 전 해당 기능 Flowchart 작성.

## 10. 승인 A/B 테스트 계획 (2026-08-11 사용자 추가)

구글 블로거로 8개 블로그를 아래 3축 조합으로 운영해 승인 여부를 비교한다.
"필수 페이지 4종"·"E-E-A-T 신호"는 이 문서 F1/F2 기능을 블로그별로
켬/끔한 결과이며, "대량 vs 1일1포"는 기존 오토런/스케줄러 발행 모드
차이(F5 케이던스 자동화 없이 수동 운영)다. F9 준비도 요약
(`GET .../adsense-readiness`)으로 각 블로그가 실제로 어느 버킷에
