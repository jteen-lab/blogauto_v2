# 블로그 오토 — 애드센스 승인 지원 기능 작업계획서

> **상태**: 부분 구현 진행 중(F1/F2/F5/F6/F9 최소 구현 완료, F3/F4/F7/F8/F10 미착수) · **작성일**: 2026-08-03 · **최종 갱신**: 2026-08-11(F5 발행 케이던스 조절 구현 완료) · **작성**: Claude
> **목적**: guntamoney.blogspot.com 애드센스 반려("가치가 별로 없는 콘텐츠") 재분석을 근거로,
> blogauto가 생성·발행하는 블로그의 **애드센스 승인 확률을 높이는 기능**을 설계한다.
> **주의**: 본 문서는 기능 근거·명세 초안이다. 실제 개발은 기능별 Flowchart(`docs/flowcharts/`) 선작성 후 진행한다.

---

## 1. 배경 — 반려 진단 (3개 분석 수렴)

이전 분석(메모리 `project_adsense_rejection`), 외부 AI(체셔캣) 분석, 2026 정책 재검증이 **동일 결론으로 수렴**. 반려 4대 축:

1. **신뢰/정책 페이지 부재** — 개인정보처리방침·이용약관·소개·문의 없음 → "불완전·의심 사이트" 판정.
2. **주제 산포(니치 없음)** — 은행·여행·보험·연금·가전 뒤섞임 → E-E-A-T 축적 불가, content farm 패턴.
3. **대량·고속 자동발행** — 월 최대 158개 → 2026.3 강력 시행된 **scaled content abuse** 타깃.
4. **얕은 정리형·템플릿·중복** — 공공정보 재나열(Information Gain 미달), 600자↓ thin content, 저자·출처·직접경험 전무.

### 2026 정책 핵심(설계 전제)
- **AI 생성 자체는 금지 아님.** "가치·사람 검수·E-E-A-T"를 갖추면 승인 → **자동화를 유지하되 신호를 붙이는 방향**이 유효.
- Information Gain(기존 웹에 없는 새 정보/관점) 요구, Information Redundancy 감점.
- 식별 가능한 저자·검증 가능한 전문성·편집 감독 신호 요구.
- 권장: 고품질 장문 20~30편, 재신청 전 2~3주 대기.

## 2. 목표 / 비목표

**목표**
- blogauto로 만든 블로그가 애드센스 **최소 요건 + 품질 신호**를 자동/반자동으로 충족하도록 지원.
- 발행 전/후 **준비도 진단**으로 재신청 성공률 향상.

**비목표(한계 명시)**
- 승인 **보장 아님**. "검증 가능한 전문성"·"진짜 직접 경험"은 완전 자동화 불가 → blogauto는 **신호·구조·니치·속도 관리**로 확률을 높이는 데 집중.
- 애드센스 계정 신청/심사 자동화는 범위 밖(수동).

**F10. 문의 폼 자동 생성 기능** `P1` — **설계 확정, 구현 착수 전(2026-08-18)**:
**블로거·워드프레스 통합 — 양 플랫폼 Google Forms 임베드**(도메인 무구매·자체호스팅
없음·이메일 미노출·범용 도메인이라 공개 지문 없음). 블로그별 Forms API 자동 생성 →
`contact_form_url` 자동 채움(기존 iframe 골격 재사용). **착수 전 사전 준비물 필수**:
GCP Forms API 활성화 + OAuth Forms 스코프 재동의 + WP용 운영자 구글 계정 지정.
작업계획서 `docs/plans/adsense_f10_contact_form_plan.md`, 순서도
`docs/flowcharts/adsense_f10_contact_form.md`.
- **배경**: F1 완료로 mailto 노출 문제는 `contact_form_url` 옵트인으로 해결했으나,
  현재는 폼 URL을 운영자가 Google Forms/Formspree 등 외부에서 **수동으로 하나씩
  생성**해 블로그 설정에 입력해야 함
  ([[project_contact_form_conversion]] "미해결" 항목의 후속). §10 A/B 테스트처럼
  블로그 8개 이상을 동시 운영할 경우 동일 폼 URL을 재사용하면 "동일 소유주 묶음"
  노출 위험이 커서(§10 주의) 블로그마다 서로 다른 폼이 필요한데, 수동 생성은
  확장성이 없음.
- **목표**: 블로그 등록/설정 시점에 문의 폼을 **자동 생성**하고 그 URL을
  `contact_form_url`에 자동으로 채워 운영자 수작업을 제거하고, 블로그별 폼 분리를
  기본값화한다.
- **검토할 구현 옵션(조사 필요, 우선순위 아님)**:
  1. **Google Forms API(`forms.googleapis.com`) 자동 생성** — `forms.create`로
     이름/이메일/메시지 필드를 가진 문의 폼을 자동 생성 가능. **알려진 한계**:
     API로 생성한 폼에 "응답 시 이메일 알림"을 켜는 공식 엔드포인트가 없음(현재는
     UI 수동 설정 또는 `watches` API의 Pub/Sub 알림만 가능) — 실사용 가능 여부
     조사 필요.
  2. **Formspree API 자동 생성** — 유료 플랜에서 폼을 프로그래매틱하게 생성하는
     API 제공 여부·요금제 확인 필요.
  3. **자체 호스팅 경량 폼 엔드포인트** — blogauto 서버에 블로그별 문의 폼 수신
     엔드포인트(`/contact/{blog_id}`)를 직접 구현, 제출 시 해당 블로그 소유자
     이메일로 전달(SMTP/이메일 발송 연동 필요). 외부 서비스 의존 없이 완전
     자동화 가능하나 스팸 방지(캡차 등)·이메일 발송 인프라 신규 구축 필요.
  4. **워드프레스 전용 — REST로 폼 플러그인 자동 설치+활성화** — WordPress 코어
     REST 엔드포인트 `POST /wp/v2/plugins`(WP 5.5+)가 `slug`(예: `contact-form-7`)
     지정만으로 wordpress.org 플러그인의 설치·활성화까지 처리 가능(`wp plugin
     install --activate`의 API 등가물). Application Password에 플러그인
     설치/관리 권한(관리자 계정 필요)이 있으면 동작. 설치 후 플러그인이
     생성한 숏코드(예: `[contact-form-7 id="..."]`)를 문의 페이지 본문에
     삽입하는 후처리가 별도 필요 — Contact Form 7은 REST로 폼 자체(필드
     구성)를 생성하는 공식 엔드포인트가 없어 기본 폼을 그대로 쓰거나 플러그인
     활성화 후 DB 직접 조작이 필요할 수 있음(조사 필요). `wordpress_api.py`에
     현재 `wp/v2/plugins` 연동 없음(신규 구현). **워드프레스 블로그에만 적용
     가능**(블로거는 플러그인 개념 없음 → 옵션 1/2/3 중 선택 필요).
     [[project_wordpress_seo_autoinput]]의 mu-plugin 수동 설치 사례와 달리 이
     옵션은 REST로 완전 자동화 가능하다는 점이 차별점(전제: 관리자 권한 보유).
- **권장 방향(초안)**: 플랫폼별로 분리 검토. **워드프레스는 옵션 4**(REST
  플러그인 자동 설치)가 외부 서비스 의존·요금제 제약이 없고 워드프레스
  생태계에 자연스러워 유력 — 단 Contact Form 7 폼 필드 자체를 REST로
  커스터마이즈할 수 있는지(또는 기본 폼으로 충분한지) 확인 필요. **블로거는
  옵션 3(자체 호스팅)**이 외부 API 제약(옵션1 알림 한계, 옵션2 요금제
  불확실성)에 걸리지 않아 유력. 스팸 방지(rate limit/허니팟)와 발송 인프라
  (기존 이메일 발송 로직 존재 여부) 조사 후 착수 여부 결정.
- **구현 방향(자체 호스팅 채택 시)**:
  - 블로그 등록/설정 시 `contact_form_url`을 자동으로 `/contact/{blog_id}` 형태로
    채움(운영자 수동 입력 필드는 override 옵션으로 유지, 기존 하위호환 유지).
  - 신규 라우터: 폼 렌더링 + POST 처리(rate limit/허니팟 필드로 스팸 방지) +
    블로그 소유자 이메일로 전달.
  - `required_pages_templates.py`의 iframe 임베드 대상을 자체 엔드포인트로
    지정할 수 있도록 확장(기존 외부 URL 방식과 공존).
- **영향 영역**: 블로그 등록/설정 API, `required_pages_templates.py`(iframe 대상
  URL 생성 로직), 신규 문의 폼 라우터/서비스, 이메일 발송 연동(신규 또는 기존
  재사용 여부 확인). 옵션 4(워드프레스 REST 플러그인 자동 설치) 채택 시
  `wordpress_api.py`에 `wp/v2/plugins` 설치/활성화 연동 신규 추가 필요.
- **데이터 변경**: `contact_form_url`이 자동 채움 값(자체 엔드포인트)인지 운영자
  수동 입력값(외부 URL)인지 구분할 플래그가 필요할 수 있음(조사 후 결정).
- **근거**: §10 A/B 테스트에서 8개 블로그 동시 운영 시 서로 다른
  `contact_form_url`이 필요 — 수동 생성이 병목.

- **영향 영역**: 발행 파이프라인 검증 단계.
- **근거**: thin content = 대표 반려 사유.

**F7. Information Gain 프롬프트 개편** `P2` ⭐ — **최소 구현 완료(2026-08-12)**:
`blocks.py` Q-AdsenseGain 정보이득 블록(SoT) + `content_generator_helper`가
preparing/applied 블로그에 자동 주입(옵트인·중복가드) + "애드센스 승인용"
성장 프리셋(1일1포). **UI 5번째 블록 수동선택·출처 자동삽입은 미구현**
(순서도 `docs/flowcharts/adsense_f7_information_gain.md`).
- **내용**: 생성 프롬프트를 "정보 재나열 금지 → 고유 관점·구체 팁·비교·주의점·출처 링크 포함"으로 개편. 출처 자동 인용.
- **구현 방향**: 생성 모듈 프롬프트 템플릿 개정 + 출처 수집/삽입 로직. 섹션 구성을 "무엇을/왜 유용/어떻게(구체)"로.
- **영향 영역**: 생성 프롬프트 템플릿(`prompt-form-*`, 생성 서비스).
- **근거**: Information Gain / Redundancy.

**F8. 발행 전 중복 방지(근접 중복 게이트)** `P2` — **구현 완료(2026-08-17,
경량 Jaccard 방식)**: `topic_dedup_gate.check_topic_duplicate`를
`publisher_pipeline.publish_post` F6 게이트 직후(단일 choke point)에 삽입. 같은
블로그 발행완료 글 제목과 Jaccard 유사도 비교, 보수 임계값(0.82) 이상이면
차단(`_reject_pre_publish`, log_reason="주제 중복"). **계획서의 V3 통합 식별자
게이트 재사용은 V3가 HOLD·튜닝 미완이라 발행 경로 오차단/비용 리스크로 미채택**,
경량 Jaccard로 이탈(사용자 확정). 순서도 `docs/flowcharts/adsense_f8_publish_dedup.md`.
마이그레이션 없음. 향후 임계값/on-off SystemSettings화·topic_id 병행 판정 여지.
- **내용**: 발행 직전 기존 글과 **주제 중복** 검사 → 중복이면 차단.
- **구현 방향**: **이번에 구축한 유사도 통합 식별자 게이트**([[project_similarity_unified_gate]] · `docs/flowcharts/unified_discriminator_gate.md`) + 회색지대 AI를 발행 전 검사에 재사용.
- **영향 영역**: 발행 파이프라인, `SimilarityService`/`TokenDFService`.
- **근거**: 중복·유사 콘텐츠 감점. 기존 자산 재활용으로 저비용.

**F11. 애드센스 승인 전용 프롬프트 프리셋** `P2` — **구현 완료(2026-08-17,
전용 프롬프트 방식)**: `presets.py`에 `ADSENSE_APPROVAL_PROMPT`(웹 취합 기반
전용 프롬프트) + `adsense-approval` 프리셋. 기존 4축 조합이 아니라 완성 프롬프트를
`user_prompt_template`에 그대로 채운다(`fullPromptOverride`). 적용 시 정보이득
지시 내장이라 F7 토글은 끔(이중 지시 방지), 4축·글자수·커스텀저장 비활성.
정보이득·검색의도 즉답·E-E-A-T·출처·people-first·정직 가드레일 반영, 유연 구조.
**승인 테스트로 프롬프트 적절성 검증 예정.** 순서도
`docs/flowcharts/adsense_f11_prompt_preset.md`. 마이그레이션 없음.
1차 4축-고정 구현은 사용자 정정으로 전용 프롬프트 방식으로 교체([[feedback_adsense_prompt_intent]]).
- **배경**: F7으로 정보이득 지시문 블록(Q-AdsenseGain)과 자동 주입(프롬프트
  모듈 `info_gain_enabled` 토글)은 구현됐으나, 제안서 §2.4의 **"정보이득 지시문
  + E-E-A-T 궁합이 좋은 4축(페르소나·독자·패턴·톤) 조합을 하나로 묶은 완성형
  프롬프트 프리셋"** 은 미구현. 현재는 운영자가 프롬프트 모듈에서 4축을 매번
  수동 조합하고 정보이득 토글을 따로 켜야 함.
- **내용**: 제안서 §2.4 권장 조합(예: 전문가·중급·P1·수치형 `s1-v1`,
  분석가·결정·P4·수치형 `s1-v2`, 경험·공감형 P5 + P-Friend/P-Essayist)에
  Q-AdsenseGain을 기본 포함한 **"애드센스 승인용" 프롬프트 프리셋**을 신설.
  운영자가 프리셋 하나 선택으로 "정보이득 지시문 + 근거·비교·출처 문체"가
  한 번에 적용되도록 한다.
- **구현 방향**:
  1. `prompt-builder`의 5번째 축(QUALITY: Q-None/Q-AdsenseGain) 노출(F7 잔여와
     동일 항목) — 운영자가 정보이득을 4축과 함께 직접 선택 가능하게.
  2. `blocks.py`/prompt_builder 프리셋 저장소에 "애드센스 승인용" 조합을
     기본 프리셋으로 등록(4축 코드 + quality_code=Q-AdsenseGain 고정).
  3. F7 성장 프로파일 "애드센스 승인용" 프리셋(1일1포)과 명명·UX를 맞춰
     "프롬프트 프리셋 + 성장 프리셋"이 한 쌍으로 인지되게.
- **영향 영역**: `prompt_builder`(4축 선택 UI·프리셋 저장소), `blocks.py`
  QUALITY 축 노출.
- **근거**: 제안서 §2.4. F7 지시문만으로는 "궁합 좋은 문체 조합"까지 자동화되지
  않음 — 프리셋으로 묶어야 운영 편의·일관성 확보.

> **사용자 확정 방향**: 생성/발행 관련 제어(니치·정보이득·케이던스)는 **모듈
> 단위**로 이전한다. 애드센스 승인용 모듈을 일반 모듈과 통합하거나 전용 모듈로
> 분리해 쓸 수 있어야 하므로, 블로그 전역 스위치(`blog.adsense_status`)가 아닌
> 프롬프트/성장 프로파일 모듈에서 제어한다.

- **F4 니치** → 프롬프트 모듈 `settings.niche_enabled`+`niche_topic_ids`, UI는
  카테고리 선택 근처. `blog.adsense_status` 의존 제거.
- **F7 정보이득 주입** → 프롬프트 모듈 `settings.info_gain_enabled` 토글 기반.
- **F7 프리셋** → 성장 프로파일 모듈 프리셋 목록에 "애드센스 승인용" 노출.
- **F5 일일 발행 상한** → 애드센스 탭에서 제거, 성장 프로파일 프리셋(1일1포)이
  대체. `_check_publish_cadence_cap` 게이트 제거. `adsense_status` 드롭다운은
  계정 상태 추적용으로 애드센스 탭에 유지.
- **마이그레이션 없음**(모듈 settings는 자유 JSONB). 순서도
  `docs/flowcharts/adsense_module_ui_migration.md`.
