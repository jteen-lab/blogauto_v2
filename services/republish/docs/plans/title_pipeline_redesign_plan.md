## 1. 왜 바꾸는가 — 운영 숫자

2026-09-02 운영 DB 실측.

| 항목 | 수치 | 해석 |
|---|---|---|
| `collected_urls` | 126,671건 | 287개 도메인, 도메인당 최대 801건(사이트맵 통crawl) |
| ㄴ 제목까지 수집됨 | 125,273건 (98.9%) | **URL 만 쌓인 게 아니라 제목까지 이미 긁혀 있었다** |

| `keyword_candidates` adopt | 475건 | 정본 키워드는 정상 작동 중 |

**진단이 바뀐다.** "수집이 부족했다" 가 아니라 **"수집은 과잉이고 통과율이
2% 였다"** 이다. 그래서 더 긁는 방향의 개선은 전부 헛돈다.

원인 세 가지:

1. **수집 제목을 재고로 직행시켰다** — 니치 무관·저품질·최신성 낮은 제목이
   그대로 임시제목이 됐다. 관문이 뒤에 있어 10만 건을 걸러야 했다.
2. **도메인 단위 통crawl** — 키워드 하나로 찾은 블로그의 사이트맵 801건을
   전부 가져왔다. 그 중 해당 니치와 관련된 것은 극히 일부다.
3. **URL 자산이 소비되지 않았다** — 저장 로직만 있고 회수 로직이 없었다.

## 2. 바꾸는 방향

### 2-1. 경쟁 제목: 재고 → **각도 신호**

```
[옛] 경쟁 제목 수집 ──────────────→ 임시제목(재고)   ← 저작권·최신성·니치 오염
[새] 경쟁 제목 조회 → 각도 추출 → AI 프롬프트 힌트 → 겹치지 않는 제목 생성
```

원문을 저장하지 않으므로 저작권 문제가 없고, 최신성 문제도 사라진다.
업계 권고도 순수 AI·순수 스크래핑이 아니라 **혼합**이다.

> 구현 상태: `app/services/title_gen/angles.py` 에 뼈대 완료(`use_angles`).
> 이번 작업은 여기에 **도메인 자산**을 물려 조회 대상을 좁힌다.

### 2-2. 소재: 키워드 → **질문 팬아웃**

제목을 긁는 대신 **사람이 실제로 치는 질문**을 모은다. 질문은 제목보다
니치 판정이 쉬워, 이미 만들어 둔 분류·필터를 그대로 통과시킬 수 있다.

| 소스 | 상태 | 비고 |
|---|---|---|
| 구글/네이버 자동완성 | **있음** | 키워드 수집 소스로 이미 가동 |
| 서치콘솔 실측 쿼리 | **있음** | 추측이 아닌 **내 블로그 실제 노출 질문** — 신뢰도 최고 |
| 의문사 확장(팬아웃) | **이번에 추가** | 아래 참조 |
| PAA(People Also Ask) | **하지 않음** | 아래 참조 |

**PAA 를 쓰지 않는 이유**: 구글은 PAA 를 공식 API 로 제공하지 않는다.
가져오려면 검색 결과 페이지 스크래핑이 필요한데, 약관 위반이고 차단 시
파이프라인 전체가 멈춘다. **대체가 가능하므로 감수할 이유가 없다.**

**대체안 — 의문사 확장**: 채택 키워드에 의문사·조사를 붙여 자동완성에
질의하면, 실제 검색량이 있는 질문형 쿼리만 돌아온다.

```
"전기기사 실기"
  ├ "전기기사 실기 왜"      → 자동완성 → "전기기사 실기 왜 어려운가"
  ├ "전기기사 실기 어떻게"  → 자동완성 → "전기기사 실기 어떻게 준비"
  └ "전기기사 실기 언제"    → 자동완성 → "전기기사 실기 언제 접수"
```

공식 자동완성 엔드포인트만 쓰므로 스크래핑이 아니다. 하나의 질문이 AI
검색에서 8~10개 하위 질문으로 갈라진다는 조사가 있고, 하위 질문 하나가
글 한 편의 소재가 된다. 기존 클러스터 기능(대표 글 1편 + 곁가지 N편)이
이미 이 구조다.

### 2-3. URL 12만 건 → **도메인 자산 287개**

개별 URL 은 버리고 도메인 요약만 남긴다. 데이터량 1/400, 정보는 보존.

```
collected_urls 126,671행                 niche_domains 287행
  url, domain, title, ...        ──▶      domain, platform, url_count,
  (도메인당 최대 801행)                     sample_titles(대표 제목 N개),
                                          top_keywords, first_seen, last_seen
```

남는 것은 **"이 니치에서 누가 상위에 있는가"** 라는 정보다. 각도 조회 시
이 도메인들을 우선 참조해 무관한 결과를 줄인다.

## 3. 단계별 작업

### T1. 도메인 자산 전환 *(데이터 관리 우선)*

- `NicheDomain` 모델 신설 — 도메인·플랫폼·URL수·대표 제목 샘플·대표 키워드·최초/최종 관측
- alembic `066` — `collected_urls` 를 집계해 적재한 뒤 원본 **삭제**
  - ⚠️ 되돌릴 수 없다. downgrade 는 빈 테이블만 되살린다.
  - `collected_urls` **테이블 자체는 유지** — 옛 `bulk_collect` 코드가 참조한다
- 데이터 관리 **URL 수집 탭 → 도메인 탭** 교체 (목록·검색·삭제·제외 토글)

### T2. 질문 팬아웃 소스

- `keyword_lab/sources/questions.py` — 의문사 확장 + 자동완성 재질의
- 소스 코드 `question_fanout` 등록, 키워드 모듈 폼에 토글
- 수집 결과는 기존 관문(금지어 → 분류 → 판정)을 그대로 통과

### T3. 각도 조회에 도메인 자산 연결

- `angles.fetch()` 가 `niche_domains` 를 우선 참조
- 니치 밖 도메인 결과는 각도에서 제외

### T4. 데이터 관리 제목 탭 정리

- 임시제목 10만 건 처리 — **결정 필요 항목**(§5)
- 정식제목 탭은 현행 유지(정상 작동 중)

## 4. 하지 않는 것

- 모듈(제목 생성/수집) 설정 화면 수정 — 사용자 지시로 **보류**
- `collected_urls` 테이블 DROP — 옛 코드가 참조, 데이터만 비운다
- PAA 스크래핑 — §2-2 참조
- 정식제목(`main_titles`) 구조 변경 — 정상 작동 중
