## 0. 먼저 고친 것 — AI 설정 리셋

**서버에는 저장돼 있었다.** 모듈 199 settings 확인 결과 `ai_provider=deepseek`,
`ai_model=deepseek-v4-flash`. **화면 표시만 리셋**됐고, 그 상태로 다시 저장하면

양방향 바인딩이 그 **빈 값을 formData 에 되쓴다.**

수정: 저장된 값을 항상 옵션 목록에 포함시킨다(`kwProviders`/`kwModels`).

## 1. 지금 구조의 문제 (사용자 지적이 맞다)

현재 키워드 모듈은 한 회차에 **수집 → 측정 → 분류 → 클러스터 → 제목 생성**을
통째로 돌고 최종 숫자만 남긴다. 그래서

- 중간 산출물을 사람이 검수할 자리가 없다
- 실패가 단계별로 격리되지 않는다 (AI 실패 20건이 "제목 0편" 으로만 보였다)
- 한 단계만 다시 돌릴 수 없다 (분류 기준만 바꿔 재분류 → 불가)
- 테스트 1회가 80초를 넘겨 프록시에 끊겼다 (단계가 쪼개져 있으면 각 10~20초)

**제목 생성까지 한 모듈에 넣은 것은 무리**라는 판단에 동의한다.

---

## 2. 질문 ①: 최초 키워드 수집과 연관 키워드 수집은 다른 로직인가?

### → **다르다. 기억하신 그대로다.**

기존 `collect` 모듈(`keyword_collector_service`)의 소스별 실제 동작:

| 소스 | 시드 필요 | 성격 | 저장처 |
|---|---|---|---|
| 구글 트렌드 | ❌ 없음 | **발견** — 실시간 인기 검색어(`get_trending_searches`) | `seed_keywords` |
| 네이버 데이터랩 | ⚠️ 하드코딩 5개 | 발견(을 의도했으나 시드 고정) | `seed_keywords` |
| 네이버 검색광고 | ✅ 시드 기반 | **확장** — 시드의 연관키워드 | `seed_keywords` |
| 네이버 뉴스 | ❌ | 제목 수집 | `temp_titles` |
| 구글 뉴스 RSS | ❌ | 제목 수집 | `temp_titles` |
| 네이버 웹문서 | ✅ | 제목 수집 | `temp_titles` |
| 대량 수집 | ✅ | 키워드→URL→제목 | `collected_urls`→`temp_titles` |

**확인된 결함**: 시드가 코드에 박혀 있다.
- 데이터랩: `["뉴스","이슈","트렌드","인기","화제"]`
- 검색광고: `["건강","맛집","여행","쇼핑","뷰티","육아","재테크","요리","운동","인테리어"]`

블로그 니치와 무관한 키워드가 들어오는 원인이고, 이미 메모리에 기록된 문제와 같다.

### 새 키워드 모듈과의 관계

새 모듈은 **확장 축만** 갖고 있다(시드 × 수식어 → 검색광고 연관 + 자동완성 + GSC).
**발견 축(트렌드·실시간·뉴스)이 없다.** 그래서 최신 이슈를 못 잡는다.

## 3. 질문 ②: 통합할 것인가, 별개로 둘 것인가

### → **로직은 분리, 실행은 한 모듈 안에서 순서대로** 를 권고한다.

두 축은 **입력이 근본적으로 다르다.**

```
발견(Discovery)  : 입력 없음 → 세상이 지금 무엇을 찾는가
확장(Expansion)  : 시드 필요 → 이 주제의 가지를 얼마나 뻗을 수 있는가
```

합치면 "시드 없이 도는 발견"이 시드를 요구하게 되어 지금의 하드코딩 시드 같은
땜질이 다시 나온다. 반대로 완전히 다른 모듈로 쪼개면 사용자가 두 개를 순서대로
관리해야 한다.

**권고**: 키워드 수집 모듈 하나가 두 단계를 내부적으로 순서대로 돈다.

```
[1] 발견   트렌드·데이터랩·뉴스 → 니치 필터 → 후보 시드 풀
[2] 확장   (발견 결과 + 블로그 니치 + 직접 입력 + 채택 재귀) × 수식어
           → 검색광고 연관 · 자동완성 · GSC 실측
```
발견 결과를 **바로 저장하지 않고 확장의 시드로 쓰는 것**이 핵심이다. 그러면
최신성(발견)과 커버리지(확장)를 한 번에 얻는다.

단, **발견 결과에 니치 필터를 반드시 건다.** 안 그러면 지금 기존 모듈처럼
취업 블로그에 "맛집"이 들어온다.

## 4. 질문 ③: 제목을 어떻게 만들 것인가

### 3-1. AI로만 생성할 것인가 → **아니다. 혼합이 맞다.**

업계 결론도 순수 AI·순수 스크래핑이 아니라 **하이브리드**다. AI는 변형을 대량
생성하고 의도 커버리지를 채우는 데 강하지만, 최종 판단에는 사람/실측 근거가
필요하다는 것이 공통 권고다.

블로그오토 맥락에서 각각의 위험:

| 방식 | 강점 | 위험 |
|---|---|---|
| AI 단독 | 의도별 확장, 대량, 최신 형식 | **애드센스 scaled content abuse** — 이미 반려 이력 있음(`project_adsense_rejection`) |
| 수집 단독 | 실제로 먹힌 표현, 비용 낮음 | 최신성 낮음, 무관 제목 혼입(검토서 기록) |

**권고**: 수집 제목을 **재고로 직행시키지 않고 "패턴·의도 신호"로 쓰고**,
AI가 그 패턴 위에서 의도별로 재구성한다. 즉
```
수집 제목 → 각도/형식 추출 → AI가 우리 키워드로 재구성 → 재고
```

### 3-2. 키워드로 제목을 수집하는 것은 비효율인가 → **아니다. 역할을 바꾸면 값이 크다.**

지금 비효율인 이유는 **수집한 제목을 그대로 재고로 쓰기 때문**이다.
(검토서 기록: 최신성 낮음 + 무관 제목 혼입)

역할을 바꾸면:
- **경쟁 제목 = 그 키워드에서 이미 먹히는 각도**를 알려 준다. AI 프롬프트에
  "이런 각도가 이미 있으니 겹치지 않게" 를 넣을 수 있다(정보 이득)
- 비용도 사이트맵 크롤링보다 검색 API 호출이 훨씬 싸다
- GSC 실측 쿼리와 합치면 "우리가 실제 노출된 각도"까지 반영된다

### 3-3. 임시 제목이 굳이 필요한가 → **필요하다.**

데이터 파이프라인의 표준 계층(bronze/silver/gold)이 이 질문의 답이다.
raw 계층을 두는 이유는 셋이다.

1. **재처리 가능** — 분류·필터 로직 버그를 고쳤을 때 원천에서 다시 안 긁어도 된다
2. **오염 격리** — 변환 버그가 최종 데이터를 더럽히지 않는다
3. **감사 추적** — 정식 제목이 어디서 왔는지 되짚을 수 있다

실제로 이번 실행에서도 **미분류 24편**을 임시 제목에 남겨 회수할 수 있었다.
버렸다면 AI 호출 비용만 날렸다.

**다만 지금은 승격 기준이 "분류 성공" 하나뿐이다.** 여기에 품질 기준(중복도,
정보 이득, 위험 유형)을 더해야 계층이 제 값을 한다.

## 5. 제안 구조

### 5-1. 데이터 관리 = 3계층

| 탭 | 계층 | 담는 것 | 사람이 하는 일 |
|---|---|---|---|
| **키워드** | bronze→silver | 수집된 키워드(미분류) → 지표 측정 → 분류 | 기준값 조정, 재분류, 수동 수집 |
| **임시제목** | bronze | 수집·생성된 제목 원본 | 검수, 재분류, 승격/폐기 |
| **정식제목** | gold | 검증 통과분 | 최종 재고 |

**키워드 관리(`/keyword-lab`) 화면은 데이터 관리 키워드 탭으로 흡수**한다.
지금 두 화면이 같은 개념을 따로 보여주고 있다.

### 5-2. 모듈 2개로 재편

```
① 키워드 수집 모듈 (기존 키워드 모듈 전환)
   발견 → 확장 → 측정(검색량·월 발행량·포화도) → 분류
   결과: 데이터 관리 [키워드] 탭

② 제목 생성/수집 모듈 (신규)
   분류된 키워드 → 제목 수집(경쟁 각도) + AI 생성(의도별 확장)
   → 금지어·중복·정보이득 게이트
   결과: 데이터 관리 [임시제목] → 승격 시 [정식제목]
```

두 모듈 모두 **데이터 관리 화면에서 수동 실행·단계별 테스트**가 가능해야 한다
(현재 모듈 폼 테스트 패널과 같은 방식을 단계별로).

### 5-3. 폐기·흡수 대상

| 모듈 | 처리 |
|---|---|
| 기존 `collect`(키워드 수집) | **발견 축만 살려 ①로 흡수**, 하드코딩 시드 폐기 |
| 기존 `bulk_collect`(대량 제목 수집) | 코드에 이미 `LEGACY` 표시. **제목 수집 축을 ②로 흡수** |
| `/keyword-lab` 화면 | 데이터 관리 키워드 탭으로 흡수 |

## 6. 가장 큰 걸림돌 — 키워드 테이블이 셋으로 쪼개져 있다

| 테이블 | 지표 | 현재 쓰임 | 운영 건수 |
|---|---|---|---|
| `seed_keywords` | **없음** (검색량·경쟁도 컬럼 자체가 없다) | 데이터 관리 키워드 탭 | 6,336 |
| `collected_keywords` | search_volume, competition | 연관 키워드 | - |
| `keyword_candidates` | 검색량·문서수·월발행량·포화도·판정·의도·클러스터·성과 | 새 키워드 모듈 | 406 |

**데이터 관리 키워드 탭이 `seed_keywords` 기반이라 지표를 보여줄 수가 없다.**
"수집만 된 키워드를 기준값으로 분류" 하려면 지표가 그 테이블에 있어야 한다.

### 선택지

| 안 | 방법 | 장점 | 단점 |
|---|---|---|---|
| **A** | `seed_keywords` 에 지표 컬럼 추가, `keyword_candidates` 폐기 | 화면 변경 최소 | 판정·클러스터·성과까지 옮겨야 해 컬럼이 15개 늘어남 |
| **B** | 데이터 관리 키워드 탭을 `keyword_candidates` 기반으로 교체, `seed_keywords` 6,336건 이관 | 지표·판정·클러스터가 이미 있음. 계층 구조와 맞음 | 데이터 이관 필요, 기존 수집 모듈이 `seed_keywords` 를 쓰므로 함께 전환해야 함 |
| **C** | 뷰(view)로 두 테이블 합쳐 보여주기 | 이관 없음 | 쓰기 경로가 둘로 남아 근본 해결이 아님 |

**권고: B.** 이유는 세 가지다.
- 지표·판정·의도·클러스터·성과 컬럼이 이미 `keyword_candidates` 에 있다
- 제안한 3계층 구조와 그대로 맞는다(미분류 → 측정 → 분류)
- A 는 결국 같은 컬럼을 옛 테이블에 다시 만드는 일이다

이관은 6,336행 `INSERT ... SELECT` 한 번이면 되고, 지표는 비운 채(미측정) 넣어
이후 측정 회차가 채우게 한다.

## 7. 구현 가능 여부 판단

| 항목 | 가능 | 근거 / 남은 일 |
|---|---|---|
| 발견 축 추가 | ✅ | `google_trends_service`·`naver_datalab_service`·뉴스 서비스 이미 있음. 니치 필터만 신규 |
| 단계 분리 실행 | ✅ | 실행기에 `steps` 파라미터가 이미 있다. 화면에서 단계별로 부르면 됨 |
| 단계별 수동 실행 | ✅ | 백그라운드+폴링 경로를 이번에 만들어 둠 |
| 제목 수집(경쟁 각도) | ✅ | `naver_search_service` 로 제목 확보 가능. 각도 추출 로직만 신규 |
| 제목 AI 생성 | ✅ | 이미 동작 확인(생성 36편) |
| 데이터 관리 흡수 | ⚠️ | 6장 스키마 결정이 선행돼야 함 |
| 기존 모듈 폐기 | ⚠️ | 운영 플로우가 물고 있어 전환 후 단계적으로 |

**미확인/조사 필요**
1. 네이버 데이터랩 API 로 "시드 없는 인기 검색어"를 받을 수 있는지
   (현재 코드가 하드코딩 시드를 쓰는 이유가 API 제약일 가능성)
2. 구글 트렌드 `get_trending_searches` 의 한국 결과 품질·안정성(pytrends 의존)
3. 제목 수집 시 저작권·중복 우려 — 각도만 추출하고 원문을 재고에 넣지 않으면
   문제되지 않으나, 정책 정리 필요

## 8. 제안 순서

| 단계 | 내용 | 선행 |
|---|---|---|
| **S1** | 키워드 테이블 일원화 결정(6장) + 이관 | — |
| **S2** | 데이터 관리 키워드 탭에 지표·판정·수동 분류 UI | S1 |
| **S3** | 키워드 모듈에서 제목 생성 분리 → 수집+분류 전용으로 | S2 |
| **S4** | 발견 축(트렌드·뉴스) 추가 + 니치 필터 | S3 |
| **S5** | 제목 생성/수집 모듈 신설(수집 각도 + AI 재구성) | S3 |
| **S6** | `/keyword-lab` 흡수, 기존 collect·bulk_collect 폐기 | S4, S5 |
