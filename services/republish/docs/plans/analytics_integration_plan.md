# 애널리틱스 연동 작업계획서 (P1~P4)

> 작성 2026-09-05 · 순서도 `docs/flowcharts/analytics_renewal_decision.md`

## 1. 왜 하는가

재발행이 **날짜만** 보고 돈다. 주기가 오면 잘 되는 글도 갈아엎는다.
어떤 글이 읽히는지 모르니 잘 되는 축을 늘릴 수도, 안 되는 축을 접을 수도 없다.

목표는 셋이다.

1. 유입을 대시보드에서 본다
2. **잘 되는 글은 건드리지 않는다** — 지금 없는 선택지다
3. 손볼 글은 "무엇을 더 쓸지" 를 근거를 갖고 정한다

## 2. 이미 있는 것 (새로 만들지 않는다)

| 자산 | 위치 | 재사용 |
|---|---|---|
| 구글 refresh token 저장·갱신 | `SystemSettings` + `google_oauth_helper` | GA4 토큰도 같은 방식 |
| 서치콘솔 쿼리 조회 | `keyword_lab/sources/gsc.py` | 페이지 단위 조회만 추가 |
| **URL 단위 발행 이력** | `SearchVisibilityUrl` | 성과 지표를 여기에 매단다 |
| 성과 되먹임 | `keyword_lab/feedback.py` | 키워드 → 글 단위로 확장 |
| 의도 분류 | `keyword_lab/intent.py` | 니즈 갭 분류에 그대로 |
| **보강 생성** | `renewal_generator._renewal_prompt` | `additional` 모드가 이미 있다 |

특히 마지막이 중요하다. **보강 작성 기능은 이미 구현되어 있다.**

```python
# renewal_generator.py — mode: inherit | new | additional
if mode == "additional" and text:
    extra = f"{text}\n\n[기존 글 본문 — 보존·반영하고 최신 정보를 추가해 확장하라]\n{existing_text}"
```

문제는 이것이 **블로그 단위 고정 설정**이라는 점이다. 한 블로그의 모든 글이
같은 대접을 받는다. 글마다 다르게 정하는 판단 근거가 없을 뿐이다.

`decide_renewal_plan()` 은 제목(keep/recombine)과 이미지(reuse/new)만 정한다.
여기에 **동작(keep/augment/ctr/rewrite)** 축을 더하는 것이 P4다.

## 3. P1 — GA4 연결

**할 일**

- `analytics.readonly` refresh token 저장 (GSC 와 같은 화면·같은 방식)
- `properties.list` 로 속성 목록 → 블로그와 매핑
- `blogs.analytics_config = {"property_id": "...", "hostname": "..."}`

**결정이 필요한 갈래**

속성을 블로그마다 따로 두었는지, 하나에 몰아넣었는지에 따라 갈린다.

| 구성 | 처리 |
|---|---|
| 블로그별 속성 | `property_id` 를 블로그에 저장 |
| 한 속성에 다수 | `hostName` 차원으로 분리 |

**둘 다 지원한다.** `hostname` 이 있으면 필터를 걸고, 없으면 속성 전체를 쓴다.
사용자에게 되묻지 않아도 되고, 나중에 구성을 바꿔도 코드가 안 바뀐다.

**Blogger 쪽 준비** — 설정 → 기본 → Google 애널리틱스 측정 ID 에
`G-XXXXXXXXXX` 입력. 테마 HTML 을 건드리지 않는다. 반영에 최대 24시간.

**규모** 작음. 라우터 1개, 서비스 1개, 마이그레이션 1개(blogs 컬럼).

## 4. P2 — 유입 수집

**새 테이블** `post_metrics_daily`

```
url_id      → search_visibility_urls.id
date        수집일(3일 지연 보정 후 실제 데이터 날짜)
sessions            GA4
engaged_sessions    GA4
avg_duration        GA4
clicks              GSC
impressions         GSC
position            GSC 평균 순위
```

URL 단위 행은 `SearchVisibilityUrl` 에 이미 있다. **일별 시계열만** 새로 쌓는다.
추세(감쇠 기울기)를 계산하려면 스냅숏이 아니라 시계열이어야 한다.

**조회**

```
GA4   properties.runReport
      dimensions  date, landingPage
      metrics     sessions, engagedSessions, averageSessionDuration
GSC   searchAnalytics.query
      dimensions  date, page
```

**할당량은 문제되지 않는다.** 무료 속성 기준 하루 20만 토큰·시간당 4만.
블로그 13개를 하루 한 번 도는 것은 1% 미만이다. 14개월 보관 제한은
탐색(Explorations)에만 걸리고 Data API 는 집계 테이블을 읽어 해당 없다.

**URL 매칭이 실무의 난관이다.** GA4 `landingPage` 는 경로만(`/2026/09/...html`),
GSC `page` 는 전체 URL, 우리 DB 도 전체 URL 이다. 정규화 규칙을 한 곳에 둔다
— 프로토콜·호스트·쿼리스트링·트레일링 슬래시. 매칭 실패는 건수를 로그로
남긴다. 조용히 0건이 되면 "유입이 없는 글" 로 오판해 멀쩡한 글을 갈아엎는다.

**규모** 중간. 마이그레이션 1개, 수집기 2개, 스케줄 1개.

## 5. P3 — 대시보드

- 블로그별 28일 세션·클릭 추이
- 상위 유입 글 / 유입 0 글 수
- 정식제목·재발행 화면의 글별 성과 열

**표시 원칙** — 수집 이력이 없는 구간은 0 이 아니라 "데이터 없음" 으로 둔다.
0 으로 그리면 도입 전 기간이 전부 폭락처럼 보인다.

**규모** 중간. API 2개, 위젯 1개.

## 6. P4 — 재발행 판정 (핵심)

### 6-1. 결정 매트릭스

| 세션 | 노출 | 판정 | 동작 |
|---|---|---|---|
| 있음·유지 | — | **유지** | 건드리지 않고 주기만 미룸 |
| 있음·28일 -20% 이하 | — | **보강** | `additional` + 니즈 갭 주입 |
| 없음 | 있음·8~20위 | **제목 손질** | 제목 재조합 + 도입부만, 본문 유지 |
| 없음 | 있음·20위 밖 | **보강** | `additional` + 니즈 갭 주입 |
| 없음 | 없음 | **재작성** | `new` — 지금 동작 |

**임계값 근거**(업계 통용): 90일 20% 하락, 순위 5계단 하락, 12개월 미갱신.
8~20위는 "노출은 되는데 클릭이 안 되는" 구간으로, 본문이 아니라 제목·설명
문제일 확률이 높다. 본문을 갈아엎으면 쌓인 순위를 잃는다.

**임계값은 설정으로 뺀다.** 우리 데이터로 검증되지 않은 숫자를 코드에 박으면
근거 없는 상수가 된다. 기본값만 위 표대로 둔다.

### 6-2. 데이터가 없을 때

수집 이력이 28일 미만이면 **지금 동작 그대로**(날짜 기준 재생성) 간다.
데이터가 없다고 멈추면 P4 배포 직후 한 달간 재발행이 통째로 선다.

### 6-3. 손대는 곳

```
renewal_plan.py       decide_renewal_plan() 에 action 축 추가
renewal_service.py    action 에 따라 renewal_prompt 모드를 글마다 결정
                      (블로그 설정은 기본값으로 남긴다)
```

`renewal_generator` 는 손대지 않는다 — 세 모드가 이미 있다.

**규모** 중간. 순수 함수 1개 + 배선.

## 7. 고객 니즈 분석 — 벤치마킹과 적용안

### 7-1. 유사 도구들이 하는 일

| 도구 | 방식 | 비용 |
|---|---|---|
| AlsoAsked | 구글 PAA 질문 트리, 1차 질문당 12개 후속 | $12~47/월 |
| AnswerThePublic | 자동완성 → 육하원칙 질문 바퀴 | $99/월~ |
| IntentGaps | URL 입력 → PAA 질문에 얼마나 답하는지 채점 | AlsoAsked API |

공통 논리는 하나다. **"사람들이 실제로 묻는 질문"과 "내 글이 답한 것"의 차이**
를 찾아 그 차이를 메운다.

### 7-2. 우리에게 맞는 방안 — 유료 API 없이

위 도구들은 남의 검색 데이터를 추정한다. **우리에게는 실측이 있다.**
서치콘솔은 이 URL 이 **실제로 어떤 검색어에 노출됐는지** 그대로 준다.
추정보다 정확하고, 이미 연결되어 있다.

```
1. GSC page 필터로 그 URL 의 노출 쿼리를 받는다
2. 본문에 그 쿼리의 답이 있는지 검사한다 (토큰 포함)
3. 없는 것 = 니즈 갭
4. intent.py 로 의도별 분류 (info/howto/compare/price/trouble)
5. 의도별 대표 질문을 생성 프롬프트에 주입
```

노출은 되는데 본문이 답하지 않는 질문 — 이것이 가장 확실한 보강 소재다.
사람들이 그 질문을 갖고 우리 글에 왔다는 증거가 이미 있다.

`angles.py`(경쟁 제목 각도)가 같은 자리에서 이미 돌고 있다.
**실측 쿼리를 하나 더 꽂는 것**이지 새 파이프라인이 아니다.

### 7-3. 나중에 검토할 것

PAA 를 직접 긁는 것은 권하지 않는다. 구글 이용약관 위반이고, 셀렉터가
자주 바뀌어 유지비가 크다. 유료 API 는 니즈 갭이 실제로 성과를 만드는지
확인한 뒤에 검토한다.

## 8. 순서와 규모

| 단계 | 내용 | 크기 | 선행 |
|---|---|---|---|
| P1 | GA4 연결·속성 매핑 | 작음 | — |
| P2 | 일 1회 수집 → 시계열 적재 | 중간 | P1 |
| P3 | 대시보드 표시 | 중간 | P2 |
| P4 | 재발행 판정 + 니즈 갭 | 중간 | P2 (28일 축적) |

**P4 는 데이터가 한 달 쌓인 뒤에 켠다.** 없는 데이터로 규칙을 만들면 임계값이
근거를 잃는다. 코드는 먼저 넣되 기본 비활성으로 두고, 축적 후 켠다.

## 9. 검증

- URL 매칭률 — 발행 글 대비 지표가 붙은 비율. 낮으면 정규화가 틀린 것이다
- 판정 분포 — 유지/보강/제목/재작성 비율. 한쪽으로 쏠리면 임계값을 본다
- 도입 전후 재발행 건수 — 줄어야 정상이다(잘 되는 글을 빼므로)

## 10. 열어 둔 것

- **GA4 속성 구성** — 블로그별인지 통합인지. 둘 다 지원하므로 착수는 막지 않는다
- **네이버 유입** — GA4 에 채널로 잡히지만 검색어는 안 준다. 별도 과제
- **임계값 튜닝** — 우리 데이터 한 달 뒤에 정한다
