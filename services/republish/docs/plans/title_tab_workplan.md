# 임시제목·정식제목 탭 작업계획서

> 작성 2026-09-03 · **계획만. 구현하지 않음.**
> 선행: `title_workflow_proposal.md`(제안·승인됨) · `title_pipeline_redesign_plan.md`(T1~T4 완료)
> 순서도: `docs/flowcharts/title_tab.md`(작성 예정)

승인된 방향:
- 임시제목 탭에 **수집·생성** 섹션을 넣는다(키워드 탭과 같은 체크박스 활성 구조)
- 생성은 **L1(키워드 기반) + L3(뉴스 시의성)** 을 포함
- **재조합은 정식제목 탭**으로 옮긴다(수작업) + 프롬프트 모듈 옵션은 유지·보완

## 1. 화면 구조 — 키워드 탭 승계

키워드 모듈이 쓰는 구조를 그대로 가져온다. **섹션 체크박스를 켜야 그
섹션의 설정이 열린다.** 끈 섹션은 실행되지 않는다.

```
임시제목 탭
├─ ☑ 수집   ← 도메인에서 제목을 긁어 온다
│   └─ 설정: 시드·도메인 예산·도메인당 상한·재고 상한 …
├─ ☑ 생성   ← 키워드/뉴스로 제목을 만든다
│   ├─ L1 키워드 기반
│   └─ L3 뉴스 시의성
└─ 목록 (출처 배지 · 필터 · 회수 큐 진단)
```

한 섹션만 켜면 그 기능 전용으로 쓸 수 있다. 키워드 모듈에서 `steps` 로
단계를 고르는 것과 같은 원리다.

## 2. 수집 섹션 (기존 기능 승계 + 보완)

### 2-1. 키워드 수집과의 분리 *(필수)*

**현행**: `bulk_collect` 가 키워드 수집과 제목 수집을 한 사이클에서 했다.
`from_collect_ingest.py` 가 옛 `collect` 모듈의 결과를 받아 URL 을 적재한다.

**변경**: 옛 키워드 수집은 폐기 예정이고 신규 키워드 기능이 그 자리를
대신한다. 제목 수집은 **키워드에 의존하지 않고 단독으로** 돈다.

시드 공급원을 셋 중에서 고른다.

| 시드 | 설명 |
|---|---|
| 채택 키워드 | 정본에서 `verdict='adopt'` 인 것 (권장) |
| 니치 도메인 | 이미 확보한 도메인의 새 글만 증분 수집 |
| 직접 입력 | 사용자가 URL/키워드를 넣음 |

### 2-2. 도메인 누적 vs 제목 추출 속도 *(핵심 결함)*

**관측된 문제**: 도메인은 계속 쌓이는데 제목 추출이 못 따라갔다.
실측으로 URL 126,671건 중 처리된 것은 31건(0.02%)이었다.

**원인 두 가지**:

1. **도메인당 전량 적재** — 사이트맵을 통째로 읽어 도메인 하나에서 최대
   801건을 넣었다. 니치와 관련된 글은 그중 일부인데 전부 큐에 들어갔다.
2. **유입과 처리에 공통 예산이 없다** — 새 도메인 수집과 제목 추출이
   서로를 보지 않고 각자 돌았다. 유입 > 처리면 격차는 영원히 벌어진다.

**개선안 — 재고 기반 유입 제어(backpressure)**

```
사이클 시작
  ├─ 미처리 큐 길이를 먼저 잰다
  ├─ 큐 > 상한  → 신규 도메인 수집 **건너뜀**, 추출만 수행
  └─ 큐 < 하한  → 신규 도메인 수집 허용
```

키워드 모듈의 "재고가 충분하면 회차를 건너뛴다" 와 같은 원리다.
이미 `cycle_tuning.py` 에 `BACKLOG_THRESHOLD=50`(콜백 적체)이 있으나,
그것은 Celery 콜백 적체용이고 **URL 큐 자체를 보지 않는다.**

**함께 적용할 상한 3가지**

| 설정 | 뜻 | 기본값(안) |
|---|---|---|
| `max_pending_urls` | 미처리 URL 이 이보다 많으면 신규 수집 중단 | 2,000 |
| `urls_per_domain` | 도메인 하나에서 가져올 최대 URL 수 | 30 |
| `domains_per_cycle` | 한 사이클에 새로 볼 도메인 수 | 5 |

`urls_per_domain=30` 이면 도메인 287개 × 30 = 8,610건. 지금의 12만 건과
달리 실제로 소화할 수 있는 양이다.

> 사이트맵 전량 적재를 유지할 이유가 없다. 최신순 상위 N건이면 충분하고,
> `lastmod_tracker.py` 가 이미 증분 판정을 한다.

### 2-3. 제목 대량 삭제 → 도메인 통째 처리 *(신규)*

**요구**: 한 도메인에서 추출한 제목을 일정 수량 이상 삭제하면, 그 도메인과
추출 제목 전체를 삭제할지 묻는다. 삭제한 도메인은 재수집되지 않는다.

**설계**

```
사용자가 임시제목 N건 삭제
        ↓
삭제분을 도메인별로 집계
        ↓
한 도메인에서 (삭제 수 ≥ 임계) 또는 (삭제 비율 ≥ 임계)
        ↓
"이 도메인은 운영 방향과 맞지 않아 보입니다.
 example.com 의 남은 제목 412건도 삭제하고 재수집을 차단할까요?"
   [도메인 차단 + 제목 전체 삭제]  [제목만 삭제]  [아니오]
```

**판정 기준(안)**: 같은 도메인에서 **10건 이상** 삭제 **그리고** 그 도메인
제목의 **30% 이상**. 둘 다 만족할 때만 묻는다 — 한쪽만 보면 제목이 3건인
도메인에서 1건만 지워도 묻게 된다.

**차단 저장 위치**: `niche_domains` 에 상태를 둔다.

현재 `is_active` 는 **"각도 조회에 참조할까"** 라는 뜻이다. 재수집 차단과는
축이 다르므로 **필드를 나눈다.**

| 필드 | 뜻 | 기본 |
|---|---|---|
| `is_active` | 각도 조회 참조 여부 | true |
| `is_blocked`(신규) | 제목 재수집 차단 | false |
| `blocked_reason`(신규) | 차단 사유(수동/대량삭제) | null |
| `blocked_at`(신규) | 차단 시각 | null |

> `domain_blacklist` 테이블은 **쓰지 않는다.** 그쪽은 참조자료 크롤링에서
> 본문 추출에 실패한 도메인용이라 의미가 다르다. 섞으면 한쪽을 풀 때
> 다른 쪽이 함께 풀린다.

수집 시 `is_blocked=true` 인 도메인은 후보에서 제외한다. 니치 도메인 탭에서
차단 목록을 보고 해제할 수 있어야 한다.

### 2-4. 추가 보완 제안 *(요청하신 "다른 의견")*

| # | 제안 | 이유 |
|---|---|---|
| a | **수집 시점에 니치 필터를 건다** | 지금은 다 긁고 나중에 지운다. 통과율 2% 의 근본 원인. 제목을 저장하기 전에 금지어·분류를 태우면 임시제목이 애초에 덜 쌓인다 |
| b | **도메인 품질 점수** | 도메인별 (정식제목 승격 수 ÷ 추출 수)를 기록해, 승격률이 낮은 도메인을 먼저 차단 후보로 보여 준다. 2-3 의 수동 판단을 데이터가 돕는다 |
| c | **수집을 '보충' 으로 격하** | L1 생성이 주력이 되면 수집은 생성이 못 채운 니치를 메우는 보조다. 재고가 목표치를 넘으면 수집 섹션은 자동으로 쉰다 |

## 3. 생성 섹션 — L1 + L3

### 3-1. L1 키워드 기반 *(구현 완료, 미가동)*

```
채택 키워드 → 질문 팬아웃 → 클러스터 → 각도 조회(니치 도메인 우선)
            → AI 제목 → 관문(금지어·분류·유사도) → 정식제목
```

`title_gen` 모듈이 이미 전부 갖고 있다. **한 번도 실행된 적이 없을 뿐이다**
(`temp_titles` 에 `collection_stage='keyword_module'` 0건).

임시제목 탭에서 할 일은 **같은 실행기를 화면에서 부르는 것**이다. 키워드
탭의 "🔎 키워드 수집" 패널과 같은 구조 — 모듈과 다른 코드를 타면 한쪽에서만
나는 버그가 생긴다.

설정 항목(모듈 설정에서 승계): 대상 블로그 · 검증 모드 · 클러스터 사용 ·
묶음당 제목 수 · 단독 키워드당 제목 수 · 각도 참고 · 제목 AI.

### 3-2. L3 뉴스 시의성 *(신규 구현)*

**AI 가 못 하는 자리**: 이번 주에 무슨 일이 있었는지 모른다. `news_collect`
로 이미 18,315건이 들어와 있다.

**원문을 재고에 넣지 않는다.** L2(각도 신호)와 같은 원칙이다.

```
뉴스 제목/요약 → 요지 추출("무슨 일이 있었나")
              → 우리 니치 키워드와 결합
              → AI 제목 → 같은 관문 → 정식제목
```

예: `전기요금 개편안 발표`(뉴스) + `전기기사`(니치)
→ "전기요금 개편이 전기기사 수요에 미치는 영향"

**설정 항목**: 뉴스 소스 · 조회 기간(일) · 결합할 니치 키워드 수 ·
회차당 제목 수 · 시의성 만료일(이 날짜가 지나면 재고에서 내림).

**시의성 만료가 필요한 이유**: 뉴스 기반 제목은 2주 뒤에 쓰면 이미 낡았다.
L1 제목에는 없는 성질이므로 `expires_at` 을 둔다.

**기존 18,315건 처리**: 원문이라 그대로 쓸 수 없다. 임시제목 정리(B안)의
니치 판정을 그대로 적용하고, 남는 것도 **소재로만** 쓴다.

## 4. 재조합 — 정식제목 탭으로

### 4-1. 위치 이동

| | 지금 | 변경 |
|---|---|---|
| 실행 위치 | 생성 프롬프트 모듈(발행 직전 자동) | **정식제목 탭(수작업)** + 모듈 옵션 유지 |
| 결과 | 휘발(글에만 반영) | **정식제목으로 저장** |

검색량·포화도를 재조합이 보지 않는다는 지적은 **해소된다.** 새 파이프라인
에서는 키워드 단계에서 이미 지표로 판정하고, 임시제목 관문을 통과한 것만
정식제목이 되기 때문이다. 정식제목을 재조합하면 그 판정을 물려받는다.

### 4-2. 결과를 같은 그룹에 넣는다

**요구**: 재조합 결과를 정식제목 탭에 그룹화하되 유사 제목 그룹과 구분한다.
별도 그룹이 아니라 **같은 그룹 안에서 별도 표기**한다.

**설계** — `MainTitle` 에 필드 2개를 더한다.

| 필드 | 뜻 |
|---|---|
| `recombined_from_id`(신규) | 원본 정식제목 ID. 있으면 재조합 결과 |
| `recombine_style`(신규) | 어떤 스타일로 만들었는지 |

- `group_id` 는 **원본 것을 그대로 물려받는다** → 같은 그룹에 묶인다
- `is_group_representative` 는 원본이 유지 → 대표는 바뀌지 않는다
- 목록에서 `recombined_from_id` 가 있으면 **`♻ 재조합` 배지**를 단다

기존 유사도 그룹과 섞이지 않는 이유: 유사 제목은 `similarity_score` 로
묶인 것이고, 재조합 제목은 `recombined_from_id` 로 출처가 명시된다.
같은 그룹 안에서 두 종류가 필드로 구분된다.

### 4-3. 재조합 제목을 고르면 재조합을 건너뛴다

**요구**: 생성 프롬프트가 재조합 제목을 선택하면 재조합을 다시 하지 않는다.

**구현 지점**: `generator.py` 2단계.

```python
# 현재
recombine_result = await self.title_recombiner.recombine(...)

# 변경(안)
if source_title.recombined_from_id:      # 이미 재조합된 제목
    working_title = source_title.title    # 그대로 쓴다
else:
    recombine_result = await self.title_recombiner.recombine(...)
```

이중 재조합은 원문에서 두 단계 멀어져 키워드가 유실된다.

### 4-4. 발행 후 회피

**요구**: 글이 완성되면 재조합 제목에 매칭해 다음 글에서 피한다.

**이미 되는 부분**: 재조합 제목도 `main_titles` 행이므로 `status='used'`,
`use_count`, `last_used_at` 이 자동으로 걸린다. 재고 선택은 `available` 만
보므로 다시 뽑히지 않는다.

**추가로 필요한 것**: 원본을 함께 소진할지 결정해야 한다.

| 안 | 동작 | 결과 |
|---|---|---|
| A | 재조합 제목만 used | 원본이 남아 **같은 소재로 또 쓴다** |
| B | 원본도 함께 used | 소재 1개 = 글 1편 |
| **C (권장)** | **그룹 전체를 used** | 유사 제목까지 함께 소진 — 같은 소재 중복 발행을 확실히 막는다 |

C 는 기존 그룹 개념과도 맞다. 그룹은 "같은 소재의 변형들" 이므로 하나를
쓰면 나머지도 쓸 이유가 없다.

### 4-5. 프롬프트 모듈 옵션 보완 *(제안서 A·B·C 적용)*

모듈 내 자동 재조합은 유지하되 지적한 세 가지를 고친다.

| 안 | 내용 | 비고 |
|---|---|---|
| **A** | `generation_history` 에 `title_style` 기록 → GSC 성과와 대조 → **성과 가중 무작위** 선택 | 지금은 `random.choice` 라 5개 스타일을 굴리며 아무것도 배우지 않는다 |
| **B** | 재조합 프롬프트에 **핵심 키워드** 동봉 | `main_titles.keywords` 를 넣어 유실 방지 |
| **C** | 재조합 결과를 **유사도 검사**에 태워 겹치면 1회 재시도 | 재조합은 관문 밖이라 지금은 무검사 |

## 5. 단계별 작업

| 단계 | 내용 | 선행 |
|---|---|---|
| **W1** | 임시제목 탭 섹션 골격(체크박스 활성) + 출처 배지·필터 | — |
| **W2** | 생성 L1 실행 패널 (모듈과 같은 실행기) | W1 |
| **W3** | 수집 섹션 — 키워드 분리 + 유입 제어(2-2) | W1 |
| **W4** | 도메인 차단 (`is_blocked` 외 3필드 · 마이그레이션 067) + 대량삭제 확인 흐름 | W3 |
| **W5** | 재조합 정식제목 탭 이동 (`recombined_from_id`·`recombine_style` · 마이그레이션 068) + 건너뛰기 + 그룹 소진(C) | — |
| **W6** | 모듈 옵션 보완 A·B·C (`title_style` 컬럼 포함) | W5 |
| **W7** | 생성 L3 뉴스 시의성 (`expires_at` 포함) | W2 |
| **W8** | 회수 큐 진단(미분류 사유 요약) | W1 |

**권장 순서 근거**: W2 를 먼저 두는 이유는 L1 이 한 번도 안 돌았기 때문이다.
무엇이 잘못됐는지 볼 수단이 없으면 나머지 설계도 근거 없이 하게 된다.

### 마이그레이션 예정

| 번호 | 내용 | 되돌리기 |
|---|---|---|
| 067 | `niche_domains` 에 `is_blocked`·`blocked_reason`·`blocked_at` | 가능(컬럼 삭제) |
| 068 | `main_titles` 에 `recombined_from_id`·`recombine_style` | 가능 |
| 069 | `generation_history` 에 `title_style` | 가능 |
| 070 | `temp_titles`/`main_titles` 에 `expires_at`(L3용) | 가능 |

전부 컬럼 추가라 되돌릴 수 있다. 데이터 삭제는 없다.

---

## 6. 하지 않는 것

- 옛 `bulk_collect` 모듈 **삭제** — 실행 경로는 보존한다(신규 생성만 차단)
- `domain_blacklist` 테이블 전용(참조자료 크롤링) — 축이 달라 섞지 않는다
- 수집 제목의 **재고 직행 부활** — 통과율 2% 의 원인
- PAA 스크래핑 — 공식 API 없음, 자동완성으로 대체 가능

## 7. 확인이 필요한 기본값

구현 전에 정하면 좋은 숫자들. 정하지 않으면 아래 값으로 시작한다.

| 항목 | 제안값 |
|---|---|
| `max_pending_urls` (유입 중단 임계) | 2,000 |

| `domains_per_cycle` | 5 |

| 그룹 소진 정책 | **C (그룹 전체)** |
