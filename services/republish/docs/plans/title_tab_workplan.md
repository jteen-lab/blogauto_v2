## 1. 화면 구조 — 키워드 탭 승계

키워드 모듈이 쓰는 구조를 그대로 가져온다. **섹션 체크박스를 켜야 그
섹션의 설정이 열린다.** 끈 섹션은 실행되지 않는다.

```
임시제목 탭
├─ ☑ 수집   ← 도메인에서 제목을 긁어 온다
│   └─ 설정: 시드·도메인 예산·도메인당 상한·재고 상한 …
├─ ☑ 생성   ← 키워드/뉴스로 제목을 만든다
│   ├─ L1 키워드 기반
│   └─ L3 뉴스 시의성
└─ 목록 (출처 배지 · 필터 · 회수 큐 진단)
```

한 섹션만 켜면 그 기능 전용으로 쓸 수 있다. 키워드 모듈에서 `steps` 로
단계를 고르는 것과 같은 원리다.

## 2. 수집 섹션 (기존 기능 승계 + 보완)

### 2-1. 키워드 수집과의 분리 *(필수)*

**현행**: `bulk_collect` 가 키워드 수집과 제목 수집을 한 사이클에서 했다.
`from_collect_ingest.py` 가 옛 `collect` 모듈의 결과를 받아 URL 을 적재한다.

**변경**: 옛 키워드 수집은 폐기 예정이고 신규 키워드 기능이 그 자리를
대신한다. 제목 수집은 **채택 키워드를 시드로 받아 단독으로** 돈다.

시드 공급원을 셋 중에서 고른다.

| 시드 | 설명 |
|---|---|
| 채택 키워드 | 정본에서 `verdict='adopt'` 인 것 (권장) |
| 니치 도메인 | 이미 확보한 도메인의 새 글만 증분 수집 |
| 직접 입력 | 사용자가 URL/키워드를 넣음 |

**제목 ↔ 채택 키워드 연결이 필요하다** *(중요)*

지금 `temp_titles.source_keyword_id` 는 옛 `collected_keywords` 를 가리킨다.
새 정본은 `keyword_candidates` 라 **연결이 끊겨 있다.**

이 연결이 없으면 §4-6(확장 재조합)이 성립하지 않는다. "이 제목은 어떤
채택 키워드로 찾았는가" 를 모르면 그 키워드로 확장할 수 없다.

→ `temp_titles`·`main_titles` 에 `candidate_id`(신규)를 두어 정본 키워드를
   가리키게 한다. 수집·생성 양쪽에서 채운다.

### 2-2. 도메인 누적 vs 제목 추출 속도 *(핵심 결함)*

**관측된 문제**: 도메인은 계속 쌓이는데 제목 추출이 못 따라갔다.
실측으로 URL 126,671건 중 처리된 것은 31건(0.02%)이었다.

**원인 — 도메인이 한 번 밀리면 다시 꺼내지지 않는다**

옛 흐름은 이랬다.

```
키워드 수집 → 키워드로 제목 검색 → 검색된 제목이 속한 도메인 저장
           → 목표 제목 수(예: 1,000개)를 채우면 사이클 종료
```

도메인 하나에서 목표를 다 채우지 못하는 경우가 흔한데, 그때 **중단된
도메인은 저장만 되고 다시 꺼내어 추출하지 않았다.** 다음 사이클은 또
새 키워드로 새 도메인을 찾는다. 그래서 도메인만 쌓였다.

**해법 — 수집과 추출을 분리한다** *(2026-09-03 재정의)*

두 동작을 **제목 수집 모듈 안의 별개 기능**으로 나눈다. 하는 일이 다르다.

| 기능 | 하는 일 | 설정 |
|---|---|---|
| **① 제목 수집** | 채택 키워드로 검색 → **제목을 얻고** 그 제목이 있던 도메인을 등록 | 시드 키워드 수 · 키워드당 수집 제목 수 |
| **② 도메인 추출** | 등록된 도메인의 **사이트맵을 읽어** URL 을 뽑고 각 URL 에서 제목 | 1회 추출 URL 수 |

```
① 채택 키워드 N개 → 순차 검색 → 설정한 수만큼 제목
                  → 제목은 바로 임시제목으로
                  → 그 제목의 도메인만 니치도메인에 등록 (URL 은 안 캔다)

② 니치도메인 → 사이트맵 전체 읽기 → URL 목록
             → 각 URL 에서 제목 → 임시제목
```

**상한을 두지 않는다** *(초판의 잘못을 정정)*

초판은 도메인당 URL(30) · 회차당 새 도메인(5) · 미완료 도메인 상한(50)을
걸었다. 그 결과 운영에서 **교착**이 났다.

```
① 미완료 도메인 277개 > 상한 50 → 영구히 건너뜀
② 티스토리를 검색으로 못 읽음   → done 으로 못 바꿈
              ↓
      미완료가 줄지 않아 ①도 영원히 안 돎 → 둘 다 0건
```

세 상한을 모두 **없앤다**. 수집은 수집만 한다.

- **도메인당 URL 상한 없음** — 제한하면 다음 회차에 같은 도메인을 중복
  수집하거나, 못 가져온 URL 을 영영 놓친다
- **회차당 새 도메인 상한 없음** — 개연성이 없다
- **미완료 도메인 상한 없음** — 추출을 분리했으므로 따로 막을 이유가 없다

**사이트맵 URL 수도 자르지 않는다.** 2~3백 개인 곳도, 1만 개가 넘는 곳도
있다. 801개로 자르면 캘 수 있는 것을 버린다.

**1회 추출 URL 수는 회차 전체의 예산이다**(도메인당이 아니다).

```
예산 100 · A에 30개 남음  → A에서 30개 캐고 B로 넘어가 70개 더
예산 100 · A에 500개 남음 → A에서 100개만, 다음 회차에 101번째부터 이어서
```

이어 캐는 위치는 `extracted_count` 다. **그 기록이 없어서 도메인이
방치됐다.**

**도메인 진행 상태**

| 필드 | 뜻 |
|---|---|
| `extract_status` | pending / partial / done / blocked |
| `extracted_count` | 사이트맵에서 어디까지 캤는가(= 이어 캘 위치) |
| `url_count` | 사이트맵의 **실제** URL 수(관측) |
| `last_extracted_at` | 마지막 추출 시각 |

### 2-3. 제목 대량 삭제 → 도메인 통째 처리 *(신규)*

**목적**: 결이 맞지 않는 도메인의 제목을 여러 페이지 넘겨 가며 하나씩
지우지 않기 위한 **수작업 보조 도구**다. 자동 삭제가 아니다.

**판정 기준 — 횟수만 본다** *(비율 기준 폐기)*

비율을 함께 보면 제목이 100건인 도메인에서 30건을 지워야 반응한다.
운영자는 보통 **3~5건만 봐도** 결이 다름을 안다. 그때 바로 물어야 한다.

| 설정 | 뜻 | 기본값 |
|---|---|---:|
| `domain_delete_threshold` | 같은 도메인에서 이만큼 지우면 묻는다 | 5 (사용자 설정, 3~20) |

**동작**

```
사용자가 임시제목 삭제 (여러 번에 걸쳐도 누적)
        ↓
같은 도메인 삭제 횟수 ≥ 임계
        ↓
[팝업] example.com — 이 도메인의 남은 제목 412건
  ┌──────────────────────────────────────────┐
  │ ☑ 전기요금 인상 총정리                    │
  │ ☑ 쿠키런 킹덤 공략                        │
  │ ☐ 전기기사 실기 후기                      │
  │ …                                        │
  └──────────────────────────────────────────┘
  [전체 선택] [선택 삭제] [전체 삭제 + 도메인 차단] [닫기]
```

한 화면에서 남은 제목을 **전부 보고** 일괄·선택 삭제한다. 페이지를 넘길
필요가 없다. 도메인 차단은 선택 사항으로 둔다 — 제목만 정리하고 도메인은
살려 두고 싶은 경우가 있다.

**삭제 횟수는 어디에 쌓는가**

세션 중 누적이 아니라 **도메인 단위로 DB 에 남긴다.** 오늘 3건, 내일 3건을
지워도 임계에 걸려야 한다.

| 필드 | 뜻 |
|---|---|
| `deleted_title_count`(신규) | 이 도메인에서 삭제된 제목 누계 |

**차단 저장 위치**: `niche_domains` 에 상태를 둔다.

현재 `is_active` 는 **"각도 조회에 참조할까"** 라는 뜻이다. 재수집 차단과는
축이 다르므로 **필드를 나눈다.**

| 필드 | 뜻 | 기본 |
|---|---|---|
| `is_active` | 각도 조회 참조 여부 | true |
| `is_blocked`(신규) | 제목 재수집·추출 차단 | false |
| `blocked_reason`(신규) | 차단 사유(수동/대량삭제) | null |
| `blocked_at`(신규) | 차단 시각 | null |

> `domain_blacklist` 테이블은 **쓰지 않는다.** 그쪽은 참조자료 크롤링에서
> 본문 추출에 실패한 도메인용이라 의미가 다르다. 섞으면 한쪽을 풀 때
> 다른 쪽이 함께 풀린다.

차단된 도메인은 ①수집·②추출 양쪽에서 제외한다. 니치 도메인 탭에서 차단
목록을 보고 해제할 수 있어야 한다.

### 2-4. 니치 필터 — **이미 있다** *(앞선 제안 정정)*

앞서 "수집 시점에 니치 필터를 건다" 고 제안했으나 **부정확했다.** 코드를
확인한 결과 제목 수집에 이미 두 가지가 걸려 있다.

| 단계 | 위치 | 상태 |
|---|---|---|
| 금지어 필터 | `chunk_processor._match_title_filter()` | **동작 중** |
| 카테고리 분류 | `chunk_processor._ensure_classifiers()` | **동작 중** |

운영 필터는 **167개 전부 `target_type='both'`** 라 키워드와 제목에 같이
걸린다. 누적 차단 실적 18,848건. 질문하신 "키워드 필터가 함께 동작하는가"
에 대한 답은 **예, 이미 함께 동작한다** 이다.

**그러면 왜 니치 무관 제목 22,501건이 남았는가**

필터와 분류가 보는 것이 다르기 때문이다.

| 검사 | 묻는 것 | 결과 |
|---|---|---|
| 금지어 필터 | "금지어가 들어 있나" | 통과 |
| 카테고리 분류 | "어느 주제인가" | 통과(주제 붙음) |
| **활성 니치 대조** | **"그 주제를 쓰는 블로그가 있나"** | **검사하지 않음** |

`쿠키런 킹덤 공략` 은 금지어가 없고 "게임" 으로 분류도 된다. 그런데 우리
블로그 중 게임을 쓰는 곳이 없으면 **영원히 안 쓰이는 재고**가 된다.
22,501건이 정확히 이 경우다.

**보완 제안 — 저장 시점 니치 대조 (신규 검사 1개)**

```
제목 → 금지어 필터 → 카테고리 분류 → [신규] 활성 니치 대조 → 저장
                                          ↓ 무관
                                     저장하지 않음(또는 표시만)
```

`BlogCategory` 에서 활성 `topic_id` 집합을 읽어 대조한다. 임시제목 정리
(B안)가 **사후에** 하는 판정을 **저장 전에** 하는 것이다. 같은 기준을 쓰므로
새 로직이 아니다.

> **주의**: 활성 카테고리가 없으면 이 검사를 건너뛴다. 카테고리를 아직 안
> 붙인 상태에서 전량 차단되면 수집이 통째로 멈춘다. 정리 기능의 가드와
> 같은 원칙이다.

**동작 방식은 선택 가능하게 둔다** — 초기에는 "표시만" 이 안전하다.

| 모드 | 동작 |
|---|---|
| 차단 | 니치 무관이면 저장하지 않는다 |
| **표시(기본)** | 저장하되 목록에서 `니치 무관` 배지 + 필터 제공 |

### 2-5. 도메인 품질 점수 *(채택)*

도메인별로 **(정식제목 승격 수 ÷ 추출 제목 수)** 를 기록한다.

| 필드 | 뜻 |
|---|---|
| `promoted_count`(신규) | 이 도메인 제목 중 정식제목이 된 수 |
| `quality_score` (계산값) | `promoted_count / extracted_count` |

용도 셋:

1. **차단 후보 제시** — 승격률이 낮은 도메인을 목록 상단에 띄운다.
   §2-3 의 수동 판단을 데이터가 돕는다
2. **추출 우선순위** — ②도메인 추출이 승격률 높은 도메인부터 본다
3. **각도 조회 우선순위** — 승격률 높은 도메인의 제목이 더 나은 각도 신호다

> 표본이 적을 때 점수는 못 믿는다. 추출 10건 미만인 도메인은 `-` 로 표시하고
> 정렬에서 뺀다.

### 2-6. 수집을 '보충' 으로 격하 — **보류** *(결정 유예)*

앞서 "L1 이 주력이 되면 수집은 보조" 라고 제안했으나 **지금 정할 문제가
아니다.**

옛 수집이 성과가 없었던 이유는 수집 방식 자체가 아니라 **검색량·포화도를
보지 않고 무작위 발행 제목을 긁었기 때문**이다. 지금은 키워드 단계에서
지표로 걸러 "채택" 을 만든다.

**채택 키워드로 검색해 모은 제목**이라면 이야기가 다르다. 거기에 §4-6
확장 재조합까지 붙으면 생성과 결과가 크게 다르지 않을 수 있고, **물량은
수집이 압도적**이다.

→ 우열은 추측으로 정하지 않는다. **양쪽을 다 구현하고 실측으로 정한다.**

비교 지표(§2-5 를 그대로 쓴다):

| 지표 | 생성(L1) | 수집(채택 키워드 기반) |
|---|---|---|
| 정식제목 승격률 | ? | ? |
| 회차당 산출량 | ? | ? |
| 발행 후 GSC 노출 | ? | ? |

두 경로에 `source` 를 남겨 두면 나중에 이 표를 채울 수 있다. **W1 단계에서
출처 기록부터 정확히 해 둔다.**

## 3. 생성 섹션 — L1 + L3

### 3-1. L1 키워드 기반 *(구현 완료, 미가동)*

```
채택 키워드 → 질문 팬아웃 → 클러스터 → 각도 조회(니치 도메인 우선)
            → AI 제목 → 관문(금지어·분류·유사도) → 정식제목
```

`title_gen` 모듈이 이미 전부 갖고 있다. **한 번도 실행된 적이 없을 뿐이다**
(`temp_titles` 에 `collection_stage='keyword_module'` 0건).

임시제목 탭에서 할 일은 **같은 실행기를 화면에서 부르는 것**이다. 키워드
탭의 "🔎 키워드 수집" 패널과 같은 구조 — 모듈과 다른 코드를 타면 한쪽에서만
나는 버그가 생긴다.

설정 항목(모듈 설정에서 승계): 대상 블로그 · 검증 모드 · 클러스터 사용 ·
묶음당 제목 수 · 단독 키워드당 제목 수 · 각도 참고 · 제목 AI.

### 3-2. L3 뉴스 시의성 *(신규 구현)*

**AI 가 못 하는 자리**: 이번 주에 무슨 일이 있었는지 모른다. `news_collect`
로 이미 18,315건이 들어와 있다.

**원문을 재고에 넣지 않는다.** L2(각도 신호)와 같은 원칙이다.

```
뉴스 제목/요약 → 요지 추출("무슨 일이 있었나")
              → 우리 니치 키워드와 결합
              → AI 제목 → 같은 관문 → 정식제목
```

예: `전기요금 개편안 발표`(뉴스) + `전기기사`(니치)
→ "전기요금 개편이 전기기사 수요에 미치는 영향"

**설정 항목**: 뉴스 소스 · 조회 기간(일) · 결합할 니치 키워드 수 ·
회차당 제목 수 · 시의성 만료일(이 날짜가 지나면 재고에서 내림).

**시의성 만료가 필요한 이유**: 뉴스 기반 제목은 2주 뒤에 쓰면 이미 낡았다.
L1 제목에는 없는 성질이므로 `expires_at` 을 둔다.

**기존 18,315건 처리**: 원문이라 그대로 쓸 수 없다. 임시제목 정리(B안)의
니치 판정을 그대로 적용하고, 남는 것도 **소재로만** 쓴다.

## 4. 재조합 — 정식제목 탭으로

### 4-1. 위치 이동

| | 지금 | 변경 |
|---|---|---|
| 실행 위치 | 생성 프롬프트 모듈(발행 직전 자동) | **정식제목 탭(수작업)** + 모듈 옵션 유지 |
| 결과 | 휘발(글에만 반영) | **정식제목으로 저장** |

검색량·포화도를 재조합이 보지 않는다는 지적은 **해소된다.** 새 파이프라인
에서는 키워드 단계에서 이미 지표로 판정하고, 임시제목 관문을 통과한 것만
정식제목이 되기 때문이다. 정식제목을 재조합하면 그 판정을 물려받는다.

### 4-2. 결과를 같은 그룹에 넣는다

**요구**: 재조합 결과를 정식제목 탭에 그룹화하되 유사 제목 그룹과 구분한다.
별도 그룹이 아니라 **같은 그룹 안에서 별도 표기**한다.

**설계** — `MainTitle` 에 필드 2개를 더한다.

| 필드 | 뜻 |
|---|---|
| `recombined_from_id`(신규) | 원본 정식제목 ID. 있으면 재조합 결과 |
| `recombine_style`(신규) | 어떤 스타일로 만들었는지 |

- `group_id` 는 **원본 것을 그대로 물려받는다** → 같은 그룹에 묶인다
- `is_group_representative` 는 원본이 유지 → 대표는 바뀌지 않는다
- 목록에서 `recombined_from_id` 가 있으면 **`♻ 재조합` 배지**를 단다

기존 유사도 그룹과 섞이지 않는 이유: 유사 제목은 `similarity_score` 로
묶인 것이고, 재조합 제목은 `recombined_from_id` 로 출처가 명시된다.
같은 그룹 안에서 두 종류가 필드로 구분된다.

### 4-3. 재조합 제목을 고르면 재조합을 건너뛴다

**요구**: 생성 프롬프트가 재조합 제목을 선택하면 재조합을 다시 하지 않는다.

**구현 지점**: `generator.py` 2단계.

```python
# 현재
recombine_result = await self.title_recombiner.recombine(...)

# 변경(안)
if source_title.recombined_from_id:      # 이미 재조합된 제목
    working_title = source_title.title    # 그대로 쓴다
else:
    recombine_result = await self.title_recombiner.recombine(...)
```

이중 재조합은 원문에서 두 단계 멀어져 키워드가 유실된다.

### 4-4. 발행 후 회피

**요구**: 글이 완성되면 재조합 제목에 매칭해 다음 글에서 피한다.

**이미 되는 부분**: 재조합 제목도 `main_titles` 행이므로 `status='used'`,
`use_count`, `last_used_at` 이 자동으로 걸린다. 재고 선택은 `available` 만
보므로 다시 뽑히지 않는다.

**추가로 필요한 것**: 원본을 함께 소진할지 결정해야 한다.

**결정: C — 그룹 전체를 `used` 로** (2026-09-03 승인)

| 안 | 동작 | 결과 |
|---|---|---|
| A | 재조합 제목만 used | 원본이 남아 같은 소재로 또 쓴다 |
| B | 원본도 함께 used | 소재 1개 = 글 1편 |
| **C ✅** | **그룹 전체를 used** | 유사 제목까지 함께 소진 |

그룹은 "같은 소재의 변형들" 이므로 하나를 쓰면 나머지도 쓸 이유가 없다.

> 되돌릴 여지는 남긴다. 그룹 소진은 `status` 변경이라 되돌릴 수 있고,
> 정식제목 탭의 **복원** 기능이 이미 있다.

### 4-5. 프롬프트 모듈 옵션 보완 *(제안서 A·B·C 적용)*

모듈 내 자동 재조합은 유지하되 지적한 세 가지를 고친다.

| 안 | 내용 | 비고 |
|---|---|---|
| **A** | `generation_history` 에 `title_style` 기록 → GSC 성과와 대조 → **성과 가중 무작위** 선택 | 지금은 `random.choice` 라 5개 스타일을 굴리며 아무것도 배우지 않는다 |
| **B** | 재조합 프롬프트에 **핵심 키워드** 동봉 | `main_titles.keywords` 를 넣어 유실 방지 |
| **C** | 재조합 결과를 **유사도 검사**에 태워 겹치면 1회 재시도 | 재조합은 관문 밖이라 지금은 무검사 |

### 4-6. 확장 재조합 — **참고 사항** *(반드시 구현은 아님)*

**착상**: 생성이 채택 키워드로 제목을 **확장**하듯, 재조합도 원본 제목을
확장할 수 있다. 다만 원본은 이미 완성된 문장이라 한계가 있다.

**한계를 인정하고 쓸 수 있는 자리 두 곳**

**① 최신성 갱신** *(효과가 분명함)*

완성된 제목이 만들어진 시기가 낡으면 그대로 쓸 수 없다.

```
"2024년 전기기사 실기 접수 일정"   ← 2026년에 쓰면 죽은 제목
        ↓ 최신성 재조합
"2026년 전기기사 실기 접수 일정"
```

판정은 규칙으로 가능하다 — 제목에 **연도·분기·"최신"·"올해"** 가 있고
`created_at` 이 오래됐으면 갱신 대상이다. AI 없이도 후보를 고를 수 있고,
문장 다듬기만 AI 가 한다.

| 필드 | 뜻 |
|---|---|
| `freshness_checked_at`(신규) | 마지막 최신성 점검 시각 |

**② 키워드 축 확장** *(연결이 있어야 가능)*

원본 제목의 채택 키워드(§2-1 의 `candidate_id`)를 알면, 그 키워드의
**질문 팬아웃 결과**를 재조합 힌트로 넣을 수 있다.

```
원본:   "전기기사 실기 준비 방법"
키워드: "전기기사 실기" → 팬아웃: "왜 어려운가" / "언제 접수" / "얼마나 걸리나"
        ↓
확장:   "전기기사 실기, 접수는 언제부터인가"
```

이것이 되면 §2-6 의 "수집 + 확장 재조합이 생성을 대체할 수 있는가" 를
실제로 시험할 수 있다.

> **전제**: `candidate_id` 연결(§2-1)이 없으면 ②는 불가능하다. ①은 연결
> 없이도 된다. → **①을 먼저**, ②는 연결이 깔린 뒤에.

## 5. 단계별 작업

**전 단계 완료 (2026-09-03).** 아래 표의 상태 열을 참조.

**모듈 이식 (2026-09-04)**: 임시제목 탭 작업대의 수집·추출·생성(L1/L3)을
`title_gen` 모듈에 이식했다. 플로우·오토런이 `TitleWorkbench.run_for_module`
을 타므로 **화면과 모듈이 같은 코드**를 쓴다. 옛 모듈은 `collect`/`gen` 키가
없으므로 생성만 켜진 것으로 읽는다 — 짐작해서 수집까지 켜면 사용자가
모르는 사이 수집이 시작된다.

| 단계 | 내용 | 상태 |
|---|---|---|
| **W1** | 임시제목 탭 섹션 골격(체크박스 활성) + **출처 기록·배지·필터** | 완료 |
| **W2** | 생성 L1 실행 패널 (모듈과 같은 실행기) | 완료 |
| **W3** | 수집 섹션 ①제목 수집 — 키워드 분리 + `candidate_id` 연결 | 완료 |
| **W4** | 수집 섹션 ②**도메인 추출** — 진행 상태(`extract_status`) + 유입 상한 | 완료 |
| **W5** | 도메인 차단 + 대량삭제 팝업(남은 제목 일괄/선택 삭제) | 완료 |
| **W6** | 도메인 품질 점수(승격률) + 추출·차단 우선순위 반영 | 완료 |
| **W7** | 재조합 정식제목 탭 이동 + 건너뛰기 + 그룹 소진(C) | 완료 |
| **W8** | 모듈 옵션 보완 A·B·C (`title_style` 기록·성과 가중) | 완료 |
| **W9** | 확장 재조합 ① 최신성 갱신 | 완료 |
| **W10** | 생성 L3 뉴스 시의성 (`expires_at`) | 완료 |
| **W11** | 저장 시점 니치 대조(표시 모드) | 완료 |
| **W12** | 회수 큐 진단(미분류 사유 요약) | 완료 |
| **W13** | 확장 재조합 ② 키워드 축 (팬아웃 힌트) | 완료 |
| **W14** | **니치 추천 — 규칙 기반**(§9-2). 미분류 어휘 빈도 → 후보 + 회수 예상 건수 + 그 자리에서 추가 | 완료 |
| **W15** | **taxonomy API**(§9-4) plan/apply/history/rollback + 감사 로그 | 완료 |
| **W16** | 니치 추천 — **AI 배치 제안**(§9-3). 승인/거부/보류함 | 완료 |
| **W17** | 저장 시점 니치 대조를 **차단 모드**로 전환(선택) | 완료 |

**권장 순서 근거**

- **W1 을 맨 앞에** 두는 이유는 출처 기록 때문이다. §2-6 의 "생성이냐 수집이냐"
  를 나중에 실측으로 정하려면 지금부터 출처가 남아야 한다. 뒤늦게 붙이면
  그 사이 데이터는 비교 불가다.
- **W2 를 그다음**에 두는 이유는 L1 이 한 번도 안 돌았기 때문이다
  (`keyword_module` 산 제목 0건). 무엇이 잘못됐는지 볼 수단이 없으면
  나머지 설계도 근거 없이 하게 된다.
- **W4(도메인 추출)가 W3 바로 뒤**인 이유는 그것이 12만 건 방치의 직접
  해법이기 때문이다.
- **W14(규칙 기반 니치 추천)를 W15(API)보다 앞에** 두는 이유: 추천은 AI 도
  API 도 없이 되고, 효과(회수 건수)를 바로 잴 수 있다. 그 숫자를 보고
  W15·W16 이 필요한지 판단하면 된다. 반대로 하면 도구부터 만들고 쓸 데를
  찾게 된다.
- **W17(니치 대조 차단 모드)을 W14 뒤**에 두는 이유: 분류표가 얇은 상태에서
  차단부터 켜면 살릴 수 있는 제목까지 막힌다. 추천으로 분류표를 채운 뒤에
  잠근다.

## 6. 하지 않는 것

- 옛 `bulk_collect` 모듈 **삭제** — 실행 경로는 보존한다(신규 생성만 차단)
- `domain_blacklist` 테이블 전용(참조자료 크롤링) — 축이 달라 섞지 않는다
- 수집 제목의 **재고 직행 부활** — 관문을 거치지 않는 저장은 하지 않는다
- 수집의 **주력/보조 서열 확정** — §2-6, 실측 후 결정
- PAA 스크래핑 — 공식 API 없음, 자동완성으로 대체 가능
- 사이트맵 **전량 적재** — 최신순 상위 N건으로 대체
- 운영 서버에 **클로드 코드 CLI 내장**(§9-5 B안) — 밖에서 호출(A안)로 충분
- 분류표 **자동 적용** — 니치 변경은 사람 승인을 반드시 거친다
- 전체 설정 API 를 **한 번에 개방** — §9-6, 카테고리부터 단계적으로

| taxonomy API 개방 범위 | **1차 카테고리만** | §9-6 |

## 8. 이번 검토에서 새로 드러난 것

계획을 다시 훑으며 확인한 사항. 앞선 제안의 정정 2건을 포함한다.

| # | 내용 | 영향 |
|---|---|---|
| 1 | **니치 필터는 이미 있다**(§2-4). 앞선 "필터가 없다" 는 제안은 부정확했다. 빠진 것은 금지어·분류가 아니라 **활성 니치 대조** 하나뿐이다 | 작업량 감소 |
| 2 | **제목 ↔ 정본 키워드 연결이 끊겨 있다**(§2-1). `source_keyword_id` 가 옛 `collected_keywords` 를 가리킨다. 이 연결 없이는 확장 재조합(§4-6 ②)이 불가능 | 마이그레이션 068 필수 |
| 3 | **도메인 진행 상태가 없다**(§2-2). 밀린 도메인을 "밀렸다" 고 기록할 자리가 없어 영원히 방치됐다. 상태 필드가 분리의 전제 | 마이그레이션 067 필수 |

| 5 | 삭제 횟수를 **DB 에 누적**(§2-3). 세션 단위로 세면 오늘 3건·내일 3건이 임계에 안 걸린다 | 필드 1개 추가 |
