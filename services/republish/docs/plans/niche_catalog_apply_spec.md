## 1. 질문 1 — 제안한 니치는 blogauto의 어느 계층인가?

**주제(Topic) 레벨이 맞다.** blogauto 카테고리는 3계층이다.

```
Topic(주제)  →  SubTopic(하위 주제)  →  Keyword(키워드)
  예: 보험    →   자동차보험          →  "자동차보험 비교", "다이렉트 자동차보험"
```

**중요 — 각 계층의 실제 역할이 다르다.**

| 계층 | 역할 | 비고 |
|---|---|---|
| Topic | 니치 단위. 통계·필터의 상위 축 | 제목은 topic_id도 보유 |
| **SubTopic** | **블로그 카테고리 설정의 단위** | `BlogCategory`는 subtopic 기준으로 저장 |
| **Keyword** | **수집 제목의 자동 분류 사전** | `category_matcher_service`가 이 사전으로 제목을 카테고리에 매칭 |

→ **키워드는 장식이 아니라 분류 엔진의 입력이다.** 키워드가 비면 수집한 제목이
해당 니치로 분류되지 않아 재고가 쌓이지 않는다. 현재 키워드는 `대출 정보` 66개,
`여행 정보` 59개 등 일부 하위주제에만 존재한다.

## 2. 질문 2 — 하위 주제 · 키워드 설계안

배정안(니치 재설계 제안서 4장)에 포함된 니치 위주로 정리한다.
키워드는 **매칭 사전**이므로 (a) 제목에 실제로 등장할 표현, (b) 다른 니치와 겹치지 않는 표현
두 조건을 만족해야 한다.

### 2.0 키워드 표기 규칙 — `+` 조합 (2026-08-23 코드 확인 반영)

**확인 결과**: `category_matcher_service._is_keyword_match()` 가 `+` 조합을 지원하며
**순서는 무관**하다.

```python
if "+" in keyword:
    parts = [p.strip().lower() for p in keyword.split("+")]
    return all(part in text_lower for part in parts)   # AND · 순서 무관
```
- `보험+방법` → 제목에 "보험"과 "방법"이 **둘 다** 있으면 매칭
- `방법 ... 보험` 순서로 등장해도 매칭된다(위치가 아니라 포함 여부만 본다)
- 부분은 2개 이상 가능: `AI+이미지+생성` 처럼 3개도 동작

**현재 데이터**: 키워드 532개 중 **477개(90%)가 이미 조합 형태**다.
다만 두 가지 용법이 섞여 있다.
1. 의도된 AND 조건 — `공기청정기+정보`, `윈도우+업데이트`
2. 공백 대체 — `Stable+Diffusion`, `Microsoft+Excel` (하나의 고유명사를 `+`로 이은 것)
2번도 AND로 동작하므로 무해하나, **설계 의도를 구분해 기록**해 둘 필요가 있다.

#### 신규 키워드 작성 3원칙
1. **일반명사 단독 등록 금지** — `방법` `정보` `신청` `조건` `비용` `가격` `후기` `종류`
   같은 범용어는 **반드시 니치 앵커와 결합**한다.
   - ❌ `방법` (→ "태아보험 가입 방법"이 생활정보로 빨려간다)
   - ✅ `보험+방법`
2. **앵커는 니치 고유어로** — 다른 니치에 거의 등장하지 않는 단어를 첫 부분에 둔다.
   - `실손+청구`, `전세+대출`, `양도+세`, `요양+등급`
3. **고유명사·제도명은 단독 허용** — 다른 니치와 충돌하지 않는 경우에 한한다.
   - `햇살론`, `버팀목`, `부모급여`, `청년도약계좌`, `제왕절개`

#### 매칭 우선순위의 한계 (설계 시 주의)
정렬 기준은 `priority 오름차순 → 키워드 문자열 길이 내림차순`이며 **첫 매칭에서 즉시 반환**한다.
- 길이는 `+` 를 포함한 **원문 문자열 길이**다. `보험+방법`(5) > `방법`(2) 이므로
  같은 priority면 조합이 먼저 평가된다 — 의도대로 동작한다.
- 그러나 **조합의 실질 강도(부분 개수)는 정렬에 반영되지 않는다.**
  `암+보험`(4)은 단일 `이비인후과`(5)보다 뒤로 밀린다.
- **대안**: 니치 전속 키워드에 `priority` 를 낮게(=우선) 부여해 길이 의존을 줄인다.
  현재 분포는 priority 1이 18개, 4가 31개, 5가 470개, 6이 13개다.
  - 신규 고단가 니치 키워드: **priority 3**
  - 범용 니치(생활정보·여행): **priority 6**
  로 두면 길이와 무관하게 니치가 먼저 잡힌다.

#### 실제 동작 검증 (2026-08-23, 순수 함수 직접 호출)
| 케이스 | 키워드 | 제목 | 결과 |
|---|---|---|---|
| 정방향 | `보험+방법` | 태아보험 가입 **방법** | ✅ 매칭 |
| **역순** | `보험+방법` | **방법**을 알려주는 태아**보험** 가이드 | ✅ 매칭 — **순서 무관 확인** |
| 일부만 | `보험+방법` | 태아보험 가입 절차 | ❌ 미매칭(정상) |
| 3개 조합 | `AI+이미지+생성` | AI 이미지 생성 방법 | ✅ 매칭 |
| 3개 중 일부 | `AI+이미지+생성` | 이미지 생성 도구 | ❌ 미매칭(정상) |
| 붙여쓰기 | `자동차+보험` | **자동차보험** 비교 | ✅ 매칭(부분 문자열이라 띄어쓰기 무관) |
| **문제 사례** | `방법`(단독) | 태아보험 가입 **방법** | ⚠️ 매칭 — 생활정보로 흡수됨 |

## 3. 질문 3 — 카테고리 관리에 자동 반영 가능한가?

| 주제 | `POST /api/v1/categories/topics` |

키워드 약 250개 규모.

## 4. 질문 4 — 블로그별 카테고리 설정도 반영되는가?

**API는 있으나, 그것만으로는 실제 발행에 반영되지 않는다.** 이게 가장 중요한 발견이다.

### 4.1 카테고리 설정이 두 군데 있다
| 저장 위치 | 단위 | 설정 경로 | 현재 데이터 |
|---|---|---|---|
| `blog_categories` 테이블 | subtopic | `POST /blogs/{id}/settings/categories` | **161건** |
| 프롬프트 모듈 `settings.blog_category_map` | blog+topic+subtopic | 모듈 편집 화면 | 11개 모듈 전부 보유(2~26건) |

### 4.2 실행 시 우선순위 — 모듈이 이긴다
`inventory_trigger` 의 제목 선택 로직:
```
1순위: 모듈 settings.categories (= blog_category_map에서 그 블로그 몫)
2순위: BlogCategory 테이블
(니치 강제가 켜져 있으면 위 둘을 모두 덮어씀)
```

→ **블로그 설정만 바꾸면 프롬프트 모듈이 있는 블로그는 아무 변화가 없다.**
현재 11개 블로그 모두 프롬프트 모듈에 `blog_category_map`을 갖고 있으므로,
**전부 해당된다.**

### 4.3 따라서 반영하려면 두 곳을 함께 고쳐야 한다
1. `blog_categories` 테이블 (API 있음)
2. 각 프롬프트 모듈의 `settings.blog_category_map` (모듈 수정 API로 가능하나 **UI가
   생성하는 구조와 정확히 같은 형태**로 써야 함)

| P1 | **설정이 두 곳**(BlogCategory / 모듈 map)이라 한쪽만 바꾸면 무효 | 반영 안 된 채 "적용했다"고 착각 | 일괄 반영 스크립트가 **양쪽을 함께** 갱신. 적용 후 실제 제목 조회로 검증 |
| P2 | **신규 니치는 제목 재고 0** | 배정 즉시 그 블로그 발행 중단 | 순서 고정: 카테고리 등록 → **키워드 등록** → 제목 수집 → 재고 확인 → 배정. 재고 임계치 미달 시 배정 보류 |
| P3 | **키워드 없으면 자동 분류가 안 됨** | 수집해도 니치에 안 쌓임 | 니치 등록과 **키워드 등록을 한 트랜잭션**으로. 하위주제당 최소 5~10개 |
| P4 | 키워드가 기존 니치와 겹침(예: "대출"이 생활정보에도) | 오분류·중복 | 등록 전 **기존 키워드와 충돌 검사**. 우선순위(priority) 필드로 조정 |
| P4-1 | **범용어 단독 키워드가 니치 제목을 흡수** ("방법"이 "태아보험 가입 방법"을 생활정보로) | 니치 재고가 생활정보로 샘 | 신규는 전부 `+` 조합으로 등록(2.0 규칙). **기존 단일 범용어도 점검해 조합으로 전환** |
| P4-2 | 정렬이 문자열 길이 기준이라 짧은 조합이 긴 단일에 밀림 | 간헐적 오분류 | 신규 고단가 니치 `priority 3`, 범용 니치 `priority 6` 으로 분리 |
| P5 | 기존 제목 이동(생활정보 `금융 정보` 164건 → 금융/대출) | 이미 발행된 글의 카테고리가 바뀜 | 발행 이력은 `crawled_posts`에 별도 보관되므로 발행분은 영향 없음. 단 **통계·필터 표시가 달라짐**을 사전 고지 |
| P6 | 테스트 잔재 삭제 시 연결 데이터 | 소프트 삭제라 데이터는 남지만 목록에서 사라짐 | 삭제 전 **연결된 제목 수 확인**(현재 대상 13건은 전부 제목 0건 → 안전) |
| P7 | 대량 등록 중 실패 | 일부만 등록된 어중간한 상태 | **드라이런 모드** 먼저(등록될 내용만 출력) → 확인 후 실제 등록. 실패 시 롤백 |
| P8 | 니치 전환으로 과거 글과 주제 불일치 | 블로그 정체성 혼란 | 급전환 금지. **신규 발행부터 점진 전환**, 과거 글은 그대로 |
| P9 | 모듈 map을 코드로 직접 수정 | UI가 기대하는 형식과 어긋나면 편집 화면이 깨짐 | 형식을 UI 생성 결과와 1:1로 맞추고, **적용 후 모듈 편집 화면을 반드시 열어 확인** |
| P10 | 니치 강제(F4)가 켜진 모듈 | 카테고리 설정 자체가 무시됨 | 니치 강제 모듈은 **니치 topic만 바꾸면 됨**. 카테고리 반영 대상에서 제외 |

## 6. 권장 적용 절차 (착수 시)

```
0) 백업 (categories·subtopics·keywords·blog_categories·modules)
1) 드라이런 — 등록/삭제/이동 대상 전체 출력, 사용자 확인
2) 정리 — 테스트 잔재 삭제, 중복 병합, 금융 정보 이동
3) 신규 니치 등록 — 주제 → 하위주제 → 키워드 (한 번에, priority 포함)
3-1) **매칭 검증** — 기존 제목 3,090건을 새 키워드로 재분류 시뮬레이션(쓰기 없이),
     오분류·미분류 건수를 보고 키워드 조정
4) 제목 수집 — 니치별 재고 확보 (임계치: 하위주제당 30건)
5) 재고 확인 — 미달 니치는 배정 보류
6) 블로그 배정 — BlogCategory + 모듈 blog_category_map 동시 갱신
7) 검증 — 블로그별로 실제 선택되는 제목을 조회해 니치 일치 확인
8) 모듈 편집 화면 육안 확인
```

**4~5번을 건너뛰면 6번 직후 발행이 멈춘다.** 이 순서는 타협 대상이 아니다.

## 7. 규모 추정
- 신규 주제 7개 / 하위주제 약 45개 / 키워드 약 250개 (**전부 `+` 조합 표기**)
- 정리 대상: 삭제 13건(잔재) + 주제 3개, 병합 4쌍, 이동 2건(164+105)
- 블로그 배정: 11개 블로그 × (BlogCategory + 모듈 map)

작업 자체는 스크립트로 수 분이면 끝나지만, **4번(제목 수집)이 실제 소요 시간을 좌우**한다.
