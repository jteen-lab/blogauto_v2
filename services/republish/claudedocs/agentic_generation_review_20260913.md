## 0. 결론 먼저

**네 가지를 확인했습니다.**

1. **화면 제어는 Claude에서 됩니다.** `browser_toolset_20260801`은 **클라이언트 툴셋**이라 브라우저를 우리가 호스팅합니다. 즉 블로그 오토에 **이식이 가능한 구조**입니다.
2. **브라우저 실행 기반이 이미 서버에 있습니다.** `docker/Dockerfile:32`에 `RUN playwright install chromium`이 들어 있고, 지금은 스타일 URL 추출에만 쓰입니다. 0부터 시작하지 않습니다.
3. **수작업과 자동 생성의 품질 차이는 모델 탓이 아닙니다.** 구조 문제입니다. 현재 생성은 **검색 1회 → 요약 1회 → 글 생성 1회**로 끝나는 단발 파이프라인이고, 에이전트의 **판단-재검색 루프가 없습니다.**
4. **최신성은 정렬만 하고 검증하지 않습니다.** `sort_by_freshness()`는 날짜순으로 밀어낼 뿐 배제하지 않고, 날짜를 못 읽는 문서도 그대로 통과합니다.

## 2. 수작업 글이 더 나았던 이유

모델 등급 차이도 있지만, 그걸 빼고도 **구조적으로 다섯 가지가 다릅니다.**

### ① 쟁점 설정 단계가 없다

수작업에서는 질문을 읽고 **"이 주제의 진짜 쟁점이 뭔가"** 를 먼저 정했습니다.

| 주제 | 표면 질문 | 실제로 잡은 쟁점 |
|---|---|---|
| 퇴거 청소비 | 10만원 내야 하나 | **통상손모는 임차인 책임이 아니다** |
| 같은 건물 이사 | 일반이사 견적 | **분해·조립이 견적에서 빠진다** |
| 경유 이사 | 경유 가격 | **거리가 아니라 작업 횟수로 잡힌다** |
| 이사 종류 | 일반이냐 반포장이냐 | **"상하차만"은 용달 얘기다** |

블로그 오토는 제목에서 **검색 질의**를 뽑을 뿐, 쟁점을 세우지 않습니다. 쟁점이 없으니 글의 축도 없고, 결과적으로 검색 결과를 나열하는 형태가 됩니다.

### ② 검색이 1회로 끝난다

수작업은 **서로 다른 각도로 2~3개를 동시에** 던지고, 부족하면 다시 던집니다. 퇴거 청소 글은 `원상회복 법리` / `특약 유효성` / `보증금 분쟁 절차` 세 갈래를 따로 검색했습니다.

블로그 오토는 재작성된 질의 하나로 한 번 검색하고 끝입니다. **자료가 부실해도 그대로 글 생성으로 넘어갑니다.** 되돌아갈 경로가 코드에 없습니다.

### ③ 선별이 "포함 여부"이지 "쓸모 여부"가 아니다

`relevance.matches()` 는 개체명이 텍스트에 들어 있는지를 봅니다. 들어 있으면 통과입니다.

에이전트는 다르게 봅니다. **"이 자료가 내가 세운 쟁점에 답을 주는가"** 를 묻고, 개체명이 있어도 쓸모없으면 버립니다. 반대로 개체명이 없어도 핵심 근거면 씁니다. 퇴거 청소 글의 `통상손모` 법리는 원래 질문에 없던 단어였습니다.

### ④ 구조가 주제에 맞춰 설계되지 않는다

수작업 글은 매번 구조가 달랐습니다. 퇴거 청소는 **법리 → 특약 → 금액 → 대응 절차**, 경유 이사는 **비교 → 요금 구조 → 동선 → 적재**. 쟁점이 다르니 구조도 달라진 겁니다.

블로그 오토는 프롬프트의 고정 구조를 따릅니다.

### ⑤ 자체 검증이 없다

수작업에서는 매 글마다 돌렸습니다.

- AI 상투어 13종 스캔
- 금지 태그(`blockquote`, `<style`, `target=`, `rel=`) 스캔
- 1인칭 서술 빈도 측정

블로그 오토는 길이만 봅니다.

## 3. 최신성 검증

영상이 지적한 지점이 우리에게도 그대로 있습니다.

**현재**: `relevance.sort_by_freshness()` — postdate가 있는 문서를 최신순으로 앞에, 날짜를 못 읽는 문서는 뒤로.

```python
dated   = [r for r in results if freshness_key(r)[0] == 1]
undated = [r for r in results if freshness_key(r)[0] == 0]
```

**문제 셋**

1. **정렬일 뿐 배제가 아닙니다.** 3년 전 문서도 뒤에 남아 요약에 들어갑니다.
2. **주제 자체의 시의성을 안 봅니다.** 제도가 바뀐 주제인지, 이미 지난 이슈인지 판단하는 단계가 없습니다.
3. **네이버 웹문서 postdate는 신뢰도가 낮습니다.** 재발행·수정일이 섞입니다.

영상의 대응이 적절했습니다. **뉴스 소스를 명시해 다시 뽑게 하고, 선별 기준까지 학습시킨 것** — 최근 보도와 실제 변화가 있는가, 국내 독자와 관련 있는가, 궁금증을 만드는 각도인가.

## 4. 화면 제어 — Claude에서 되는가

### 4-1. 답: 됩니다. 두 가지 툴셋이 있습니다.

| 구분 | `computer_toolset_20260801` | `browser_toolset_20260801` |
|---|---|---|
| 대상 | 데스크톱 전체 | 웹페이지 안 |
| 방식 | 스크린샷 + 좌표 | 접근성 트리 + 좌표 |
| 우리 용도 | 과함 | **적합** |

**네이버 블로그는 브라우저 툴셋이 맞습니다.**

### 4-2. 브라우저 툴셋 사양

**기본 27개 + 선택 4개**

- 이동·캡처: `navigate`, `screenshot`, `zoom`
- 포인터 11종: `left_click`, `hover`, `scroll`, `left_click_drag` 등
- 키보드: `type`, `key`, `hold_key`, `wait`
- **페이지 읽기: `read_page`(접근성 트리), `find`(자연어 요소 검색), `get_page_text`**
- 폼: `form_input`
- 탭: `new_tab`, `list_tabs`, `switch_tab`, `close_tab`
- 선택 활성화: `javascript_exec`, **`file_upload`**, `read_console`, `read_network`

지원 모델: `claude-opus-5`, `claude-sonnet-5`, `claude-opus-4-8` 등. 플랫폼은 Claude API와 Vertex AI (**AWS Bedrock 미지원**).

### 4-3. 이식 가능성 — 여기가 핵심입니다

> "Your application runs every call against its own browser automation; nothing runs on Anthropic's side."

**클라이언트 툴셋입니다.** Anthropic은 툴 스키마를 주고 모델이 "무엇을 클릭할지" 결정할 뿐, **브라우저는 우리가 띄우고 우리가 실행합니다.** 흐름은 이렇습니다.

```
Claude API → tool_use 블록 반환
    ↓
블로그 오토의 executor → Playwright로 실제 실행
    ↓
결과를 tool_result 로 반환 → 다음 턴
```

**이게 블로그 오토 구조와 잘 맞습니다.** 이미 있는 것들:

- `playwright==1.44.0` (requirements.txt)
- `RUN playwright install chromium` (docker/Dockerfile:32)
- 헤드리스 Chromium 런타임 라이브러리 (apt 단계)
- 실사용 선례 — `services/style/style_url_extractor.py`

**새로 만들어야 하는 것**은 tool_use 블록을 Playwright 호출로 옮기는 **executor 레이어**와, 네이버 로그인 세션을 유지하는 **프로필 저장소**입니다.

### 4-4. Codex 방식과의 차이

| 항목 | 영상의 Codex 방식 | Claude 이식 시 |
|---|---|---|
| 실행 위치 | 로컬 PC | **서버 컨테이너** |
| 상시 가동 | PC를 켜둬야 함 | **워커가 상시** |
| 계정 확장 | 사실상 1개 | **블로그별 프로필 분리** |
| 재시도·상태추적 | 없음 | **기존 Celery/Flow에 편입** |
| 검수 | 사람이 화면 보고 | **발행대기글로 이미 있음** |

영상 방식은 개인 운영에 맞고, **우리가 이식하면 다계정 무인 운영으로 확장됩니다.** 이게 도입 명분입니다.

### 4-5. 제약과 리스크

**기술 제약**
- 탭 최대 100개, tool_result당 상태 변경 200개
- **순차 실행 필수** — 병렬 배치에서 첫 실패 시 후속 중단
- 스크린샷이 토큰으로 과금 → 화면 제어는 **토큰 소모가 큽니다**

**보안 (문서가 명시적으로 요구)**
- 전용 저권한 계정, 신규 프로필
- 스킴 검증 (`javascript:`, `file:`, `data:`, `chrome:` 차단)
- 도메인 화이트리스트
- `file_upload` 활성화 시 전용 업로드 폴더만

**운영 리스크 — 영상이 다루지 않은 부분**
- 영상은 **하루 20개 이상 임시저장**을 합니다. 화면 제어라 봇 탐지는 피해도 **발행량과 주제 편중 패턴은 그대로 남습니다.** 네이버 기준으로 정상 범위가 아닙니다.
- 네이버 약관상 자동화 도구 사용 소지. 임시저장까지만 하고 발행은 사람이 하더라도 **계정 리스크는 우리가 집니다.**
- 에디터 DOM이 바뀌면 깨집니다. 접근성 트리 기반이라 좌표 방식보다는 낫지만 무관하지 않습니다.

## 5. 도입 후보와 우선순위

효과 대비 난이도로 정리했습니다.

| 순위 | 항목 | 효과 | 난이도 | 비고 |
|---|---|---|---|---|
| **1** | 검색 소스 확장 | 큼 | 낮음 | 뉴스·구글·법령 추가. 기존 파이프라인에 소스만 붙임 |
| **2** | 쟁점 설정 단계 | 큼 | 낮음 | 질의 재작성 앞에 "쟁점 3개 추출" 한 단계 |
| **3** | 자료 충분성 판정 + 재검색 | **큼** | 중간 | 요약 뒤 "이 자료로 쓸 수 있나" 판정 → 부족하면 질의 바꿔 1회 재검색 |
| **4** | 주제 최신성 게이트 | 중간 | 낮음 | 제목 확정 전 시의성 판정. 뉴스 소스 기반 |
| **5** | AI 흔적 검사 | 중간 | 낮음 | quality_gate에 상투어·특수문자 규칙 추가 (보류 중이라 하셨음) |
| **6** | 노출 지면 역산 학습 | 중간 | 중간 | 홈피드·검색 상위 글에서 제목·구조 패턴 추출 → 프롬프트 반영 |
| **7** | 구조 설계 단계 | 중간 | 중간 | 쟁점에 맞춰 소제목 구성을 먼저 짜고 본문 생성 |
| **8** | 네이버 화면 제어 | **큼** | **높음** | executor + 프로필 저장소 + 리스크 관리 |

**3번이 품질 격차의 핵심입니다.** 단발 파이프라인에 되돌아갈 경로 하나를 넣는 것만으로 에이전트 동작에 상당히 근접합니다. 1·2번은 그 앞단을 받쳐주는 항목이고요.

**8번은 성격이 다릅니다.** 품질이 아니라 **커버리지** 문제라 따로 판단하셔야 합니다. 네이버 블로그를 실제로 운영할 계획이 있을 때만 값이 있습니다.

## 6. 남은 판단거리

- **반자동 vs 완전자동** — 화면 제어는 임시저장까지만 하고 검수·발행은 사람이 하는 쪽이 리스크가 낮습니다. 지금 발행대기글 구조를 그대로 쓸 수 있습니다.
- **모델 등급** — 3번(재검색 루프)을 넣으면 호출 횟수가 늘어 비용이 올라갑니다. 가성비 모델로 루프를 도는 게 나은지, 상위 모델로 단발을 하는 게 나은지는 **실측이 필요합니다.**
- **적용 범위** — 전 블로그에 적용할지, 특정 니치(이사·청소처럼 근거가 필요한 주제)에만 적용할지.
