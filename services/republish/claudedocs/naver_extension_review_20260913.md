# 네이버 블로그 자동화 — 확장프로그램 방식 검토

> 작성 2026-09-13 · 코드 수정 없음, 검토 보고
> 선행 문서: `claudedocs/agentic_generation_review_20260913.md`

## 0. 전제 하나를 먼저 정정합니다

**이 영상에 나온 「AI 글 생성기」는 확장프로그램이 아니라 웹 서비스입니다.**

발표자 본인이 명시합니다.

> "AI 글 생성기는 이제 **반 자동**이에요."
> "네이버 블로그 그리고 워드프레스를 이제 수동으로 글 쓰는 것들을 **자동으로 글 쓰고 업로드는 수동으로** 하는"

실제 시연도 그렇습니다. 사이트에서 본문을 뽑고 **전체 선택 → 복사 → 네이버 에디터에 붙여넣기**를 사람이 합니다. 이미지도 직접 캡처·다운로드해서 올리고, 인용구·링크·카테고리·발행도 전부 수동입니다.

**확장프로그램이 등장하는 곳은 두 군데인데 둘 다 이 제품이 아닙니다.**

| 등장 | 정체 |
|---|---|
| 이전 영상의 "블로그 도움" | **별도 유료 상품.** "확장 프로그램만 설치하면 생성까지 다 해 준다"고 언급만 됨 |
| 이 영상의 "드래그 풀" | **서드파티 확장.** 쇼핑 상세페이지의 우클릭·드래그 방지를 풀어 움짤을 받으려고 씀 |

정정하는 이유는 이렇습니다. **이 영상이 보여주는 건 "확장으로 자동화한 사례"가 아니라, 확장 자동화를 쓰지 않고 수동 붙여넣기로 타협한 사례**입니다. 자동 입력 확장을 따로 팔면서도 시연에서는 쓰지 않았다는 점이 오히려 신호에 가깝습니다.

## 1. 서비스 구조

### 1-1. 구성

| 서비스 | 대상 | 자동화 수준 |
|---|---|---|
| **AI 글 생성기** | 네이버 블로그 / 워드프레스 | **반자동** (생성만) |
| 쿠팡 파트너스 | 워드프레스 | 완전자동 |
| 수익글 생성기 | 워드프레스 | 완전자동 |
| 여행 | 워드프레스 | 완전자동 |
| 로컬 | 워드프레스 | 완전자동 |

**패턴이 명확합니다. API가 있는 워드프레스는 완전자동, API가 없는 네이버는 반자동.** 우리와 같은 제약에 부딪혔고, 같은 선에서 멈췄습니다.

### 1-2. BYOK — 사용자가 AI 비용을 냅니다

사용자가 **Gemini API 키를 직접 발급받아 등록**합니다. 서비스는 AI 원가를 지지 않고 구독료만 받는 구조입니다.

무료 티어 한계를 영상에서 직접 짚습니다.

- **RPM 5회 / RPD 20회** — 둘 중 하나만 걸려도 발행 중단
- 그래서 Tier 1(카드 등록) 전환을 권함

**운영 팁 하나가 쓸 만합니다.** Google Cloud 프로젝트를 서비스별로 나눠 만들면(`AI글생성기-네이버`, `쿠팡오토` 등) **서비스별 소진량을 분리 추적**할 수 있습니다.

### 1-3. 요금

| 등급 | 범위 |
|---|---|
| 무료 | 전체 서비스 통틀어 **월 10회** |
| 스타터 | AI 글 생성기만 무제한 |
| 프리미엄 | 전 서비스 무제한 |

무료 워드프레스 전자책을 리드 마그넷으로 겁니다.

## 2. 워크플로우 분해

### 2-1. 자동 구간

1. **숏텐츠에서 키워드 선택** — 사이트 안에 네이버 카테고리별 인기 검색어가 들어와 있음
2. 어투 선택 (`~해요` / `~합니다` / `~한다`)
3. 목표 글자수 입력
4. **제목 먼저 생성** → 사용자가 고름
5. **본문 생성** (10~30초). 소제목 번호와 태그 포함

시연에서 1300자 설정에 **공백 제외 1500자**가 나왔습니다.

### 2-2. 수동 구간 — 여기가 실제 부담입니다

| 작업 | 비고 |
|---|---|
| 전체 선택 → 복사 → 붙여넣기 | |
| **인용구 삽입** | 발표자: "네이버가 원하는 구조를 맞추는 것" |
| 이미지 검색·캡처·다운로드·업로드 | 콜라주 배치 |
| 쇼핑커넥트 상세페이지 이미지/움짤 확보 | 우클릭 방지 해제 확장 필요 |
| **제휴 링크 삽입** | 소제목 1~2번 사이, 할인율·화살표 강조 |
| 카테고리 선택 · 발행 | |

태그만 붙여넣기 시 자동 반영됩니다.

**글 한 편에 수동 작업이 대여섯 단계입니다.** 생성이 30초라도 전체는 그렇지 않습니다.

## 3. 설계에서 눈여겨볼 세 가지

### ① 지면별 프리셋

네이버 쪽이 **다섯 갈래**로 나뉩니다.

- 홈피드
- 쇼핑 커넥트
- 쇼핑 챌린지
- 정보성
- 네이버 SE5

발표자 설명: *"홈피드 알고리즘이라든지 홈피드 시스템에 꼭 필요한 부분들을 좀 녹인 게 홈피드 스타일"*

**같은 네이버여도 노출 지면마다 요구 구조가 다르니 프롬프트를 나눈 것**입니다.

블로그 오토는 `prompt_builder/presets.py` · `presets_niche.py`로 프리셋 구조가 있지만 **축이 니치와 애드센스 단계**입니다. **지면 축이 없습니다.**

### ② 숏텐츠 — 인기 검색어를 주제 소스로

네이버 검색 결과 우측 「쇼텐츠 더보기」에 **카테고리별 인기 검색어**가 뜹니다(경제·종합·카테크 등). 다마고치는 이걸 사이트 안에 끌어와 **키워드 입력란의 소스**로 씁니다.

앞 보고서에서 1순위로 올린 **검색 소스 확장**과 바로 이어집니다. 우리 제목 수집은 `title_source.py` 기준으로 전부 **키워드가 출발점**인데, 이건 **지금 검색되는 것**이 출발점입니다.

### ③ 반자동이라는 타협

이전 영상(Codex 화면 제어)과 정반대 선택입니다.

| | 이 영상 | 이전 영상 |
|---|---|---|
| 생성 | 자동 | 자동 |
| 입력 | **수동** | 자동(화면 제어) |
| 계정 리스크 | 낮음 | 높음 |
| 손이 가는 정도 | 큼 | 없음 |

**같은 회사가 두 방식을 다 보여줬다는 게 의미 있습니다.** 자동 입력 확장을 팔면서도 주력 시연은 수동입니다.

## 4. 확장프로그램 방식 — 화면 제어와 무엇이 다른가

| 항목 | **브라우저 확장** | **화면 제어** (`browser_toolset_20260801`) |
|---|---|---|
| 실행 위치 | 사용자 PC의 브라우저 | **서버 컨테이너** |
| 세션 | **이미 로그인된 세션 그대로** | 별도 로그인·프로필 유지 |
| DOM 접근 | content script로 **직접 조작** | 접근성 트리 읽고 좌표 클릭 |
| 속도 | **즉시** | 턴당 수 초 |
| 토큰 비용 | **없음** | 스크린샷·트리가 과금 |
| 무인 운영 | **불가** (PC·브라우저 상시) | **가능** |
| 다계정 | 프로필 전환 필요 | 컨테이너 분리로 병렬 |
| 봇 탐지 | 정상 사용자 행동에 가까움 | 헤드리스 탐지 여지 |
| 배포 | 스토어 심사 또는 개발자 모드 | 서버 배포 |
| DOM 변경 대응 | 셀렉터 수정 필요 | 자연어 탐색이라 다소 유연 |

**핵심 차이는 두 줄로 요약됩니다.**

- **확장은 싸고 빠르고 안전하지만 사람이 PC를 켜야 합니다.**
- **화면 제어는 무인이지만 비싸고 느리고 리스크가 큽니다.**

## 5. 블로그 오토 적용 시나리오

### 현재 상태

`app/services/publishing/` 확인 결과 **발행 대상은 Blogger와 WordPress뿐**입니다. 네이버 발행 경로가 없습니다.

### 시나리오 A — 확장 + 서버 큐 (권장)

```
블로그 오토 서버         사용자 브라우저
─────────────────        ──────────────
글·이미지 생성            확장이 큐를 폴링
     ↓                         ↓
발행대기 큐에 적재   ──→   에디터에 자동 입력
                              ↓
                         임시저장 → 사람 검수 → 발행
```

**서버는 지금 하던 일을 그대로 합니다.** 확장은 "입력 로봇" 역할만 맡습니다.

| 장점 | 단점 |
|---|---|
| 토큰 비용 없음 | **PC를 켜둬야 함** |
| 로그인 세션 문제 없음 | 확장을 별도 개발·배포 |
| 생성 파이프라인 재사용 | 스마트에디터 DOM 의존 |
| 검수 구조(발행대기글) 그대로 | |

### 시나리오 B — 화면 제어 전면 도입

무인 운영이 되지만 토큰·리스크가 큽니다. 앞 보고서 8순위로 둔 이유가 그대로 유효합니다.

### 시나리오 C — 혼합

**네이버는 확장(반자동), 나머지는 기존 API 발행.** 화면 제어는 확장으로 안 되는 작업에만 제한적으로.

현재 구조와 가장 마찰이 적습니다.

## 6. 기술 난점 — 스마트에디터

확장을 만든다면 여기서 막힐 공산이 큽니다.

**네이버 스마트에디터 ONE은 단순 textarea가 아닙니다.** 자체 문서 모델을 쓰고 iframe 구조를 끼고 있어서, `innerHTML` 주입으로는 에디터 내부 상태가 갱신되지 않습니다. 화면에는 보여도 저장하면 사라지는 식입니다.

우회 경로는 대체로 셋인데 모두 대가가 있습니다.

1. **클립보드 붙여넣기 이벤트 합성** — 사람 동작에 제일 가깝지만 서식 보존이 불안정
2. **에디터 내부 API 호출** — 비공개라 버전이 바뀌면 깨짐
3. **키 입력 시뮬레이션** — 안정적이지만 느리고 긴 글에서 비현실적

**이미지 업로드는 더 까다롭습니다.** 파일 선택 대화상자를 거치므로 확장에서 `DataTransfer`로 파일을 밀어 넣어야 하고, 네이버가 업로드 토큰을 검증하면 그마저 막힙니다.

> 다마고치가 자동 입력 확장을 별도 상품으로 두면서도 이 영상에서는 수동 붙여넣기를 시연한 것이, **이 난이도를 반영한 결과일 가능성**이 있습니다.

## 7. 리스크

**약관.** 네이버는 자동 게시물 등록 도구를 제한합니다. **확장이라고 예외가 아닙니다.** 판단 기준은 실행 방식이 아니라 자동 등록 여부입니다.

**영상에 드러난 실제 사례.** 발표자가 쇼핑 커넥트 시연 중 이렇게 말합니다.

> "지금 19일까지 **이용 제한이 된 상태**이기 때문에 신규 링크 발급을 받을 수가 없어요. 뭐 이거는 뭐 사연이 있는데 하여튼 무시하고"

**서비스 운영자 본인 계정이 제재 중입니다.** 사유는 밝히지 않았지만, 이 영역에서 제재가 실제로 일어난다는 증거로는 충분합니다.

**배포.** 크롬 웹스토어는 자동화·스크래핑 성격의 확장을 반려할 수 있습니다. 반려되면 개발자 모드 수동 설치나 기업 배포로 가야 하고, 사용자 설치 장벽이 생깁니다.

**유지보수.** 스마트에디터가 바뀌면 셀렉터가 깨집니다. 서버 배포와 달리 **사용자가 확장을 업데이트해야** 반영됩니다.

## 8. 가져올 것

리스크와 무관하게 **지금 바로 쓸 수 있는 설계**가 셋 있습니다.

| 항목 | 현재 블로그 오토 | 난이도 |
|---|---|---|
| **지면별 프리셋** | 프리셋 축이 니치·애드센스뿐 | 낮음 |
| **인기 검색어 주제 소스** | 제목 출처가 전부 키워드 기반 | 낮음 |
| **태그 자동 생성** | `generator.py`에 태그 생성 **없음** | 낮음 |

숏텐츠는 앞 보고서 1순위(검색 소스 확장)와 묶어 처리하면 중복 작업이 없습니다.

## 9. 정리

- 이 영상의 제품은 **확장이 아니라 웹 서비스이고, 입력은 수동**입니다
- 워드프레스는 완전자동, 네이버는 반자동 — **우리와 같은 지점에서 멈췄습니다**
- 확장 방식은 **싸고 빠르고 안전하지만 무인 운영이 안 됩니다**
- 화면 제어는 **무인이지만 비싸고 리스크가 큽니다**
- 네이버를 하려면 **시나리오 A(확장 + 서버 큐)** 가 현재 구조와 가장 잘 맞습니다
- 다만 **스마트에디터 입력 난이도와 계정 리스크**가 실제 장벽이고, 영상이 그 증거를 스스로 노출했습니다
- **지면별 프리셋 · 인기 검색어 소스 · 태그 생성**은 네이버와 무관하게 지금 도입 가능합니다
