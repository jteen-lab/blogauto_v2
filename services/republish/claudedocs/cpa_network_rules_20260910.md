# 애드릭스 네트워크 규칙 — 홍보 시 지킬 규칙 정본

> 작성 2026-09-10 | 근거: 애드릭스 공지사항(금지사항 27항 + 홍보금지 카페 목록)
> 이 문서가 **모든 오퍼에 우선 적용되는 규칙의 정본**이다.

---

## 0. 규칙이 세 층이 됐다

지금까지 규칙은 오퍼 하나에 붙는 것(`CpaOffer.rules`)뿐이었다. 이번 공지로
**오퍼보다 위에 있는 층**이 생겼다.

```
L0  네트워크 규칙   애드릭스 27항 + 금지 채널 목록   ← 모든 오퍼 공통. 최우선
L1  업종 법정 규칙   의료법·변호사법·금융광고 규제    ← 업종이 걸리면 적용
L2  오퍼 규칙       광고주 가이드라인                ← 오퍼마다 다름
```

**충돌하면 L0 가 이긴다.** 광고주가 허용해도 네트워크가 금지하면 못 한다.
어기면 **수익금 지급 거절 + 서비스 이용정지**다. 글 한 편이 아니라 계정 전체가
날아간다.

## 1. 강제 방식으로 다시 나눈 27항

기계가 검사할 수 있는 것과 없는 것을 섞어 두면 아무것도 지켜지지 않는다.
**어떻게 강제할지로 다시 나눈다.**

### A. 설계로 막는다 — 코드가 애초에 그렇게 못 하도록

| 공지 | 내용 | 우리 쪽 조치 |
|---|---|---|
| 3 | 인위적 클릭·전환 프로그램 사용 금지 | **자동 클릭·자동 전환 기능을 만들지 않는다.** 어떤 형태로도 예외 없음 |
| 26 | 마케터가 상담자 정보를 **대신 입력**하는 행위 금지 | 상담자가 **링크로 직접** 랜딩에 들어가게 한다. 우리가 정보를 받아 옮기지 않는다 |
| 23 | 수집한 DB 를 여러 업체에 중복 입력 금지 | 우리는 DB 를 보관·전달하지 않는다 |
| 25 | 한 사람이 여러 캠페인에 접수되면 부정 DB | **한 글에 한 오퍼.** 여러 오퍼를 한 사람에게 몰지 않는다 |
| 16 | 생성된 URL 외 변형 금지 | **서브아이디 부착을 기본 비활성.** `subid_param` 이 오퍼에 명시된 경우에만 |
| 4·18 | 도배·성의없는 반복 금지 | 오퍼당·블로그당 **발행 상한** + 글 간 유사도 게이트 |
| 22·8·9·11·27 | 메일·문자·메신저·폐쇄 모임·지인·불법 사이트 금지 | **채널 화이트리스트.** 목록에 없는 곳에는 발행 자체를 막는다 |
| 21 | 홍보금지 카페 | 금지 채널 목록을 데이터로 관리(전체/캠페인별) |

| 공지 | 내용 |

> **검증은 클릭까지만 한다.** 전환은 실제 사용자에게서만 나와야 한다.

## 2. 대가성 문구 — 무엇을 쓰고 무엇을 쓰지 않는가

공지 24항은 웹페이지의 "사용금지문구" 마킹이 텍스트로 딸려 들어와 읽기 어렵다.
공정위 2024-12-01 개정과 대조하면 뜻이 분명해진다.

```
개정 내용: '소정의 수수료를 지급받을 수 있음' 같은 조건부·불확정 표현은
           명확하지 않은 표시문구 → 사용 불가. 확정형으로 쓸 것.
```

### 사용 순서 (2026-09-10 확정)

```
1순위  오퍼가 지정한 문구를 그대로 쓴다
       예) 안과 오퍼 — "이 포스팅은 애드릭스 수익이 발생합니다."
2순위  지정 문구가 없으면 애드릭스 대표 문구를 쓴다
       예) "애드릭스에서 홍보 활동을 통해 일정 수수료를 제공받을 수 있음"
```

**위치**: 제목 앞 `[광고]` 또는 본문 첫 부분. 끝부분 게재 불가(2024-12-01 개정).

> **남은 위험**: 공정위 개정은 "소정의 수수료를 지급받을 수 있음" 같은 **조건부
> 표현**을 "명확하지 않은 표시문구" 예시로 넣었다. 2순위 문구가 그 형태다.
> 그래서 **오퍼가 확정형을 지정했으면 반드시 1순위를 쓴다.** 2순위는 지정 문구가
> 없을 때만 쓰고, 가능하면 확정형("지급받음", "받았음")으로 바꿔 쓴다.

## 3. 채널 화이트리스트 — 27항에서 도출

공지가 채널을 직접 지목해 막았다. **허용 목록 방식으로 뒤집어 관리한다.**
목록에 없으면 금지다.

### ✅ 허용

- 자사 도메인 웹사이트·블로그 (워드프레스 등)
- 공개 블로그 (네이버 블로그, 티스토리) — 도배 금지 규칙 준수 전제
- 공개 SNS 피드 (인스타그램, 스레드 등) — 오퍼가 허용하는 경우
- **공개** 네이버 카페 (비공개·승인제 카페는 금지 — 아래 참조)
- 유료 광고 매체 (당근·메타·틱톡·구글·카카오) — **애드릭스가 채널별 픽셀 등록
  기능을 제공하므로 집행을 전제한 것으로 본다**(§8)

### ❌ 금지

| 채널 | 근거 |
|---|---|
| 카카오톡·오픈채팅·단톡방 등 메신저 | 8항 |
| 밴드, **비공개(가입 승인제) 카페**, 폐쇄 모임 | 9항 |
| 이메일, 문자메시지 | 22항 (정보통신망법 위반이기도 함) |
| 지인·친구 대상 홍보 | 11항 |
| 불법 사이트, 성인 사이트 | 27항 |
| 공지에 명시된 금지 카페 | 21항 (§4) |

### 9항 "폐쇄적"의 뜻 (2026-09-10 확인)

**폐쇄적 = 비공개.** 관리자의 승인이 있어야 가입되는 형태의 모임을 말한다.
따라서 **공개 카페는 9항에 해당하지 않아 허용**된다(§4 금지 목록 제외).

여전히 금지인 것은 메신저(8항)·단톡·밴드·승인제 비공개 카페다.
공개 카페에 쓰더라도 4·18항(도배·반복)과 21항(금지 카페)은 그대로 적용된다.

## 5. 우리 시스템과 정면으로 부딪히는 것 다섯

### ① 대량 자동 발행 (4·18항)

> "무의미한 단순 도배글로 포스팅", "성의없는 홍보문구로 지속적으로 반복"

지금 시스템의 중심 기능 — 제목 재고 40개를 만들어 대량 생성·발행 — 이 정확히
이 조항이다. **그대로 돌리면 이용정지 사유다.**

**규칙**: 오퍼당 일 발행 상한을 둔다. 글 간 유사도 상한을 둔다. 같은 오퍼로
같은 블로그에 연속 발행하지 않는다. 상한은 네트워크 기준이 없으므로 보수적으로
잡고(오퍼당 1일 1편 수준에서 시작) 관찰한다.

### ② 마케터 대리 입력 (26항) — 충돌 아님 (2026-09-10 정정)

26항은 **"상담자가 링크로 직접 들어가지 않고, 마케터가 정보를 받아 대신
입력하는 행위"** 를 막는 조항이다. 랜딩 구성을 제약하는 것이 아니다.
앞서 이를 "자체 랜딩 폼 금지"로 넓게 읽은 것은 과한 해석이었다.

**규칙**: 상담자가 **링크를 눌러 직접** 오퍼 랜딩으로 들어가게 한다. 우리가
연락처를 받아 옮기지 않는다. 애초에 자체 폼을 만들 이유가 없다 — 애드릭스가
채널별 픽셀을 오퍼 랜딩에 심어 주므로 전환 측정도 그쪽에서 된다(§8).

`consult_page.py` 는 폼 없이 `rel="nofollow sponsored"` 링크로만 넘긴다.
블로그 글에서 쓰기에 적합하고, 유료 광고는 오퍼 랜딩으로 직결해도 된다.

### ③ 서브아이디 URL 파라미터 (16항)

> "생성된 URL외에 URL을 변형하여 홍보하는 경우 이용정지 될 수 있습니다."

`subid.py` 는 랜딩 URL 에 `?subid=o12-p345-b7` 을 붙인다. 이것이 "URL 변형"에
해당하는지 공지만으로는 알 수 없다.

**규칙**: **네트워크가 서브아이디를 공식 지원한다고 확인되기 전까지 부착하지
않는다.** `subid_param` 이 오퍼에 명시적으로 설정된 경우에만 동작하도록 기본값을
비활성으로 둔다. (현재 `subid.apply()` 는 어디에서도 호출되지 않아 실제 위험은
아직 없다.)

### ④ 테스트 전환 (12~15항)

우리가 직접 상담을 넣어 전환을 확인하는 것은 **본인 단말 전환**으로 금지다.

**규칙**: 검증은 **클릭까지만** 측정한다. 전환 확인은 네트워크 리포트로만 한다.
개발·테스트 목적이라도 실제 랜딩에 신청을 넣지 않는다.

### ⑤ 채널 축소 (8·22항) — 범위 축소 (2026-09-10 정정)

막힌 것은 **메신저·단톡(8), 비공개 승인제 카페·밴드(9), 메일·문자(22)** 다.
**공개 카페는 허용**된다(§3).

남는 채널: 자사 사이트 · 공개 블로그 · **공개 카페** · 공개 SNS · 유료 광고.
앞 문서의 모델 ③은 "오픈채팅 운영"만 빠지고 공개 커뮤니티 경로는 살아 있다.

글 내용     캠페인 설명이 본문에 있어야 한다. 링크만 있는 글은 발행하지 않는다.
            사은품·혜택만 강조하지 않는다.
대가성 문구  확정형으로, 제목 앞 [광고] 또는 본문 첫 부분에.
            "~받을 수 있음" 형태의 조건부 표현은 금지어다.
링크        네트워크가 준 URL 그대로. 파라미터를 붙이지 않는다(확인 전까지).
DB          우리가 받지 않는다. 폼을 만들지 않는다. 링크로 넘긴다.

## 8. 채널별 픽셀 등록 (애드릭스 공지, 2026-09-10 확인)

> [마이캠페인] 페이지에 각 채널별 픽셀 등록 기능이 추가되었습니다.
> 페이스북(메타), 틱톡, 구글, 카카오, **당근** 픽셀 등록 가능.
> 픽셀 등록이 가능한 캠페인만 픽셀 버튼이 보입니다.
> 기존에 1:1문의로 요청했던 코드는 적용되지 않으므로 캠페인별로 다시 설정하세요.

읽히는 것 세 가지.

1. **유료 광고 집행은 사실상 허용된다.** 광고 매체 픽셀을 등록해 주는 기능은
   유료 광고를 전제하지 않으면 존재할 이유가 없다. 당근이 명시돼 있다.
2. **자체 랜딩페이지가 필요 없다.** 오퍼 랜딩에 우리 픽셀이 심어지므로
   광고 → 오퍼 링크 직결로도 유입·전환(상담 신청)이 측정된다.
3. **오퍼마다 다르다.** 버튼이 보이는 캠페인만 가능하다. 오퍼별로 확인하고,
   기존 1:1 문의 코드는 무효이므로 캠페인별로 다시 설정한다.

**규칙**: 유료 광고를 집행하는 오퍼는 **집행 전에 해당 매체 픽셀을 마이캠페인에
등록**한다. 등록 없이 집행하면 전환을 측정할 수 없어 최적화가 불가능하다.

## 9. 서브아이디 파라미터 — 무엇이고 어떻게 쓰나

### 왜 필요한가

글 100편에 상담 링크를 넣고 한 달 뒤 리포트를 보면 `상담 12건 · 승인 8건` 만
나온다. **그 12건이 어느 글에서 나왔는지는 알 수 없다.** 네트워크는 "우리
계정에서 왔다"까지만 안다.

CPA 는 글 10편이 전부를 벌고 990편이 0원인 구조다. **어느 10편인지 모르면
다음 글을 어떻게 쓸지 알 수 없다.**

### 무엇인가 — 링크에 붙이는 꼬리표

택배 송장번호와 같다. 링크마다 다른 값을 붙여 내보내면 전환이 일어났을 때
그 값이 리포트에 함께 찍힌다.

```
https://adlix.co.kr/click/12345                     ← 원래 링크
https://adlix.co.kr/click/12345?subid=blog-post-77  ← 꼬리표를 붙인 링크
                              └──── 이 부분 ────┘
```

- `?` 부터가 추가 정보 구간
- `subid` 가 **이름**, `blog-post-77` 이 **값**
- 두 개 이상은 `&` 로 잇는다 → `?subid=A&ch=instagram`

### 우리가 만드는 값 (`services/cpa/subid.py`)

```
o12-p345-b7
│    │     └── 블로그 7번
│    └──────── 글 345번
└───────────── 오퍼 12번
```

리포트에 `o12-p345-b7` 이 찍히면 *12번 오퍼를 7번 블로그의 345번 글에서
전환시켰다* 는 뜻이다. `subid.parse()` 로 되짚어 우리 DB 의 글에 붙인다.

### ⚠️ 파라미터 이름은 네트워크가 정한다

네트워크마다 `subid` · `aff_sub` · `s1` · `click_id` 등으로 다르다.
애드릭스가 지정한 이름이 아니면 **① 무시되어 아무 데도 안 찍히거나,
② 16항 "생성된 URL 외 변형"에 걸린다.**

**확인 방법 (마이캠페인)**

1. 캠페인 **링크 생성 화면**에 "서브아이디"·"sub id"·"추적값" 입력칸이 있는가
2. **리포트·통계 화면**에 서브아이디 칼럼이 있는가
3. 하나라도 있으면 지원. 없으면 1:1 문의

**확인 전까지 부착하지 않는다.** `subid_param` 이 오퍼에 명시된 경우에만 동작.

### 픽셀과 헷갈리지 않기

| | 서브아이디 | 픽셀 |
|---|---|---|
| 무엇을 아나 | **어느 글·채널에서 왔나** | **전환이 일어났다** |
| 누가 보나 | 우리 (애드릭스 리포트) | 광고 매체 (당근·메타·틱톡) |
| 어디에 붙나 | 링크 URL 뒤 | 랜딩 페이지 **안**의 코드 |
| 무엇에 쓰나 | 어떤 글을 더 쓸지 판단 | 광고 **자동 최적화** |
| 없으면 | 어느 글이 벌었는지 모름 | 광고가 학습을 못 함 |

대체재가 아니라 **보완재**다. 유료 광고에는 픽셀이, 글 여러 편에는 서브아이디가
필요하다.

## 10. 채널 구성안 — 블로그 원본 → 채널별 파생

```
콘텐츠 1건
 ├─ 원본     블로그 글 (검색 자산, 링크 본문 내)
 ├─ 파생 A   인스타 (재가공, 링크는 프로필)
 ├─ 파생 B   스레드 (재가공, 링크 본문)
 └─ 파생 C   틱톡 (영상 스크립트, 링크 프로필)
```

**맞는 점**: 전부 공개 채널이라 8·9·22항과 충돌하지 않는다. 블로그가 검색
자산을 쌓는 동안 SNS 가 유입을 늘린다. 지금 시스템이 잘하는 것(글 생성)을
살리면서 유입만 넓히는 구조라 전환 비용이 낮다.

**주의할 점 셋**

1. **같은 글을 그대로 복사하면 4·18항이다.** 원본 1 → 채널별 파생 N 을
   **실제로 다르게** 만들어야 한다. 문장만 옮기면 "성의없는 반복"으로 읽힌다.
2. **부계정 다중 운영은 위험하다.** 인스타는 수집·재업로드 계정에 제휴 링크를
   붙이는 행위를 단속 정책으로 정리했다. **채널당 1계정, 계정마다 다른 주제**.
3. **채널마다 링크 제약이 다르다.** 인스타는 본문 링크가 안 걸려 프로필 링크
   하나뿐이다. 채널별로 "링크를 어디에 두는가"를 규칙으로 가진다.

**시스템에 필요한 것**: 각 파생마다 **채널을 구분하는 서브아이디**와 **채널별
대가성 문구 위치**. 현재 `subid.py` 는 `오퍼-글-블로그` 3축이라 **채널 축을
추가**해야 한다(예: `o12-p345-b7-c2`).
