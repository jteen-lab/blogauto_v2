# 목록 화면 표시 방식 재설계 (제안)

> 2026-08-31 · 대상: 블로그 · 모듈 · 플로우 · 오토런
> 상태: **제안 — 구현 전 승인 대기**

## 1. 타당성 — 문제 제기가 맞다

카드가 나쁜 게 아니라 **개수가 임계를 넘었다.** 카드는 항목당 정보를 풍부하게
보여주는 대신 세로 공간을 많이 쓴다. 항목이 적을 때는 이득이지만 많아지면
"훑기"가 불가능해진다.

### 실제 규모

| 대상 | 개수 | 구성 |
|---|---|---|
| 블로그 | 12 | 워드프레스 6 · 블로거 6 |
| 모듈 | **32** | 프롬프트 15 · 성장프로파일 12 · 기타 5 |
| 플로우 | 14 | 블로그당 1개(12) + 수집용 2개 |

### 지금 화면에서 실제로 벌어지는 일

**모듈 화면**이 가장 심하다. 타입별 섹션은 있지만 각 섹션이 **1개만 보이고
나머지는 "더보기"로 접혀 있다**(`idx < 1`). 프롬프트 15개 중 1개만 보인다.
"인생꿀팁 프롬프트가 어떤 상태지?"를 확인하려면 섹션을 펼치고 15개 카드를
세로로 스크롤해야 한다.

**플로우 화면**은 그룹핑이 아예 없다. 14개를 한 그리드에 나열해
워드프레스용·블로거용·수집용이 섞인다.

**블로그 화면**은 플랫폼별 섹션이 이미 있다. 여기는 상대적으로 낫다.

### 구조적 관찰 — 셋이 사실상 같은 축이다

| 플로우 | 모듈 수 |
|---|---|
| 인생꿀팁_워프 | 2 |
| 군타_구글 블로거 | 3 |
| … 12개가 블로그와 1:1 | 2\~3 |
| 제목 수집 · 키워드 수집 | 1 |

**플로우 12개가 블로그 12개와 1:1로 대응하고**, 각 플로우가 프롬프트+성장
프로파일을 가진다. 즉 블로그·플로우·모듈은 서로 다른 대상이 아니라 **한
대상(블로그)의 세 단면**이다. 그런데 화면은 셋으로 나뉘어 있어, 하나를
확인하려면 화면을 오가야 한다.

이것이 "전체 정보를 인지하기 어렵다"의 진짜 원인이다. 카드냐 표냐 이전의
문제다.

## 2. 제안 — 표(테이블) 기반 + 대상 중심 통합

### 2-1. 기본형: 밀도 높은 표

카드를 표로 바꾼다. 근거는 단순하다 — **훑기와 비교는 표가 낫고, 카드는
개별 항목에 집중할 때 낫다.** 지금 필요한 것은 훑기다.

```
[블로그]  워드프레스 6 · 블로거 6 · 전체 12          [검색      ] [+ 추가]

┌ 워드프레스 ──────────────────────────────────────────────── 6개 ┐
│ 이름          애드센스   색인    글수   최근발행    상태        │
│ 인생꿀팁      ● 승인     0/103  1,044  08-30 12:0  ✓ 정상      │
│ 굿팁꿀팁      ● 승인     0/104    457  08-30 09:1  ✓ 정상      │
│ 라이프인포    ○ 준비     0/101    627  08-30 18:2  ⚠ 주의필요  │
└──────────────────────────────────────────────────────────────┘
┌ 블로거 ──────────────────────────────────────────────── 6개 ┐
│ 군타          ◐ 심사중   0/105    355  08-30 15:5  ✓ 정상      │
│ …                                                             │
└──────────────────────────────────────────────────────────────┘
```

한 행 = 한 블로그. 12개가 **한 화면에 다 들어온다.** 지금은 스크롤 서너 번이다.

- **플랫폼별 구분은 섹션 헤더**로 유지한다(이미 블로그 화면에 있는 방식).
  탭으로 나누면 "전체 몇 개인지"를 한 번에 못 본다.
- 정렬·검색은 열 머리글에서. 지금은 정렬 기준이 화면마다 다르다.
- 행 클릭 → 상세. 자주 쓰는 동작 1\~2개만 행 끝에 아이콘으로.

### 2-2. 모바일: 표를 접어 2줄 카드로

표를 가로 스크롤시키면 모바일에서 쓸 수 없다. **같은 데이터를 2줄로 접는다.**

```
┌────────────────────────────────┐
│ 인생꿀팁          ● 승인        │
│ 색인 0/103 · 1,044글 · 08-30   │
└────────────────────────────────┘
┌────────────────────────────────┐
│ 굿팁꿀팁          ● 승인        │
│ 색인 0/104 · 457글 · 08-30     │
└────────────────────────────────┘
```

지금 카드(제목+배지+본문+버튼 여러 줄)보다 **행 높이가 1/3**이다. 한 화면에
6\~8개가 보인다. 상세와 동작은 탭하면 열리는 바텀시트로 옮긴다
(`components/bottom_sheet.html`이 이미 있다).

핵심은 **데스크톱 표와 모바일 목록이 같은 데이터·같은 순서**라는 점이다.
지금처럼 모바일 전용 탭 레이아웃을 따로 두면 두 화면의 동작이 갈라진다.

### 2-3. 대상 중심 통합 — 블로그 하나로 모아 보기

블로그 목록에서 행을 펼치면 그 블로그의 플로우·모듈이 함께 보인다.

```
▼ 인생꿀팁                        ● 승인   색인 0/103   1,044글
    플로우  인생꿀팁_워프          ● 실행중   모듈 2
      ├ 프롬프트   인생꿀팁_프롬프트     🍳 요리 레시피·조리법
      └ 성장프로파일 인생꿀팁_프로파일    adsense · 1일 1개 · 8~20시
```

화면을 오가지 않고 한 블로그의 전체 구성을 본다. 모듈·플로우 화면은 **그대로
두되**(모듈을 타입별로 보고 싶을 때가 있다) 진입점을 블로그 중심으로 옮긴다.

### 2-4. 모듈 화면: "더보기" 제거

지금 각 타입에서 1개만 보이는 것이 가장 큰 문제다. 표로 바꾸면 32개가
타입별 섹션 안에 전부 들어간다. 접을 이유가 없어진다.

## 3. 왜 다른 방식이 아닌가

| 후보 | 판단 |
|---|---|
| **표 + 섹션** | **채택.** 훑기·비교·구분 모두 충족. 모바일은 2줄 목록으로 접음 |
| 탭으로 플랫폼 분리 | 전체 개수를 한 번에 못 본다. "워프 6 · 블로거 6"이 안 보임 |
| 아코디언(전부 접기) | 지금 모듈 화면의 "더보기"가 그 형태이고, 그게 문제의 원인 |
| 칸반(상태별 열) | 상태가 축이 아니다. 블로그는 상태보다 플랫폼·소속으로 나뉜다 |
| 트리 전용 | 계층은 얕다(블로그→플로우→모듈, 3단). 트리만으로는 비교가 어렵다 |
| 카드 유지 + 필터 강화 | 필터를 걸어야 보이는 건 "전체 인지"가 안 된다는 뜻 |

## 4. 작업 방식 제안

한 번에 다 바꾸지 않는다. **한 화면씩, 되돌릴 수 있게.**

| 단계 | 대상 | 이유 |
|---|---|---|
| **1** | 공용 표 컴포넌트 + 모바일 2줄 목록 | 네 화면이 같은 규칙을 쓰게. 여기서 규격을 정한다 |
| **2** | **모듈 화면** | 가장 심각(32개 중 6개만 보임). 효과가 즉시 드러난다 |
| **3** | **플로우 화면** | 그룹핑이 없어 14개가 섞여 있다 |
| **4** | **블로그 화면** | 지금도 섹션이 있어 상대적으로 덜 급하다 |
| **5** | 블로그 행 펼침(플로우·모듈 인라인) | 통합 뷰. 앞 단계가 안정된 뒤 |
| **6** | 오토런 화면 | 실행 이력은 성격이 달라 마지막에 판단 |

### 각 단계에서 지킬 것

- **한 화면씩 배포한다.** 네 화면을 동시에 바꾸면 어디서 깨졌는지 못 가린다.
- **기존 화면을 지우지 않고** 표시 방식만 교체한다. 데이터·API·동작은 그대로.
- **모바일을 같은 데이터로 만든다.** 지금처럼 모바일 전용 레이아웃을 따로
  두면 두 화면이 서로 다른 것을 보여주게 된다.
- 각 단계마다 **회귀 테스트**: 목록 개수·정렬·필터·행 동작이 그대로인지.

## 5. 예상 효과

| 항목 | 지금 | 바뀐 뒤 |
|---|---|---|
| 모듈 화면에서 보이는 개수 | 6 / 32 | **32 / 32** |
| 블로그 12개 훑기 | 스크롤 3\~4회 | **한 화면** |
| 플랫폼 구분 | 블로그만 | 전 화면 |
| 특정 항목 찾기 | 섹션 펼치고 스크롤 | 정렬·검색 |
| 모바일 한 화면 항목 수 | 2\~3 | **6\~8** |

## 6. 정직하게 덧붙임

- **표가 모든 면에서 낫지는 않다.** 항목별 정보가 많고 개수가 적을 때는 카드가
  낫다. 지금 규모(12\~32개)에서 표가 유리한 것이지, 블로그가 3개였다면 카드가
  맞았다. 앞으로 더 늘어날 것이므로 표가 맞다고 본다.
- **모바일에서 열이 줄어드는 것은 불가피하다.** 데스크톱 6열을 모바일에서 다
  보여줄 수 없어 2줄로 접는다. 무엇을 접을지는 화면마다 정해야 한다.
- 작업량은 **화면당 반나절\~하루** 수준으로 본다. 데이터·API를 건드리지 않고
  표시 계층만 바꾸기 때문이다. 5단계(통합 뷰)는 별도로 더 든다.
