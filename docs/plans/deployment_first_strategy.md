## 0. 한 줄 요약

## 2. Q1 — 인증 후행 추가가 현실적인가?

### 2.1 결론
> **매우 현실적입니다.** 인증은 BlogAuto 코어 로직과 분리 가능한 "출입 검사" 레이어이므로 나중에 부착 가능합니다.

### 2.2 비유로 이해하기
| 구분 | 비유 |
|------|------|
| 지금 배포할 BlogAuto | 혼자 사는 집 (현관 잠금만) |
| 인증 추가 | 공동주택 출입카드 시스템 부착 |
| 호환성 보장 | 집을 다시 짓지 않고 현관에 카드 리더기만 설치 |

### 2.3 후행 호환 보장을 위해 지금 해둘 것

#### A. 환경변수 토글
```env
# .env
CENTRAL_AUTH_ENABLED=false  # 지금은 비활성 (모든 사용자 통과)
CENTRAL_AUTH_URL=           # 비워둠 (인증 추가 시 입력)
```

#### B. 인증 미들웨어 자리 미리 마련
```python
# app/middlewares/auth_gate.py (지금 단계)
async def auth_gate_middleware(request, call_next):
    if not settings.CENTRAL_AUTH_ENABLED:
        return await call_next(request)  # 통과
    # 인증 추가 시 여기에 JWT 검증 로직
    ...
```

#### C. DB 컬럼 미리 추가
```sql
-- 지금 마이그레이션에 미리 포함
ALTER TABLE users ADD COLUMN grade VARCHAR(20) DEFAULT 'beta';
ALTER TABLE users ADD COLUMN instance_id VARCHAR(64) NULL;
ALTER TABLE users ADD COLUMN status VARCHAR(20) DEFAULT 'approved';
ALTER TABLE users ADD COLUMN grade_expires_at TIMESTAMP NULL;
```
→ 인증 추가 시 마이그레이션 추가 없이 바로 활용

#### D. 디렉토리 구조 분리
```
app/
├─ core/             # 코어 비즈니스
├─ auth/             # ← 미리 만들어둠 (지금은 빈 디렉토리)
│   └─ central_client.py  # 인증 추가 시 작성
└─ middlewares/      # auth_gate.py만 pass-through로
```

### 2.4 후행 추가 시 작업량 추정
| 작업 | 시간 | 비고 |
|------|-----|------|
| 중앙 서버 신규 구축 | 5일 | 이전 Phase 1과 동일 |
| BlogAuto 측 인증 적용 | **1일** | 토글만 켜기 + 미들웨어 채우기 |
| 사용자 인스턴스 일괄 업데이트 | 자동 | Watchtower로 배포 |

→ **합산 6일**. 기존 Phase 1(11.5일)보다 짧음 (배포 인프라 이미 있음).

### 2.5 후행 전 위험 요소

| 위험 | 대응 |
|------|------|
| 인증 없이 인스턴스가 외부 노출되면 누구나 사용 가능 | 초기 사용자만 IP 화이트리스트 / 직접 인스턴스 URL 전달 |
| 베타 사용자가 임의로 정보 유출 | 약관 동의 + 명시적 베타 안내 |
| 인증 추가 후 기존 사용자 강제 가입 | 자동 마이그레이션 (기존 사용자는 자동 승인 처리) |

## 3. Q2 — 초보자 클릭 배포 + 자동 업데이트

### 3.1 결론
> **가능합니다.** 단, "완전 클릭만"은 불가능합니다.  
> Oracle 서버에 **SSH로 한 번 접속**해서 **명령 한 줄**만 실행하면 됩니다.  
> 이후는 모두 자동.

### 3.2 4가지 옵션 비교

#### 옵션 A — 원클릭 설치 스크립트 + Docker + Watchtower ⭐ (권장)

**사용자가 하는 일:**
```bash
# Oracle 서버 SSH 접속 후 단 한 줄
curl -fsSL https://blogauto.com/install.sh | bash
```

**이 한 줄이 자동으로:**
1. Docker 설치 (없으면)
2. BlogAuto 컨테이너 이미지 다운로드
3. **설치 마법사 실행** (사용자에게 질문):
   - Gmail 주소 / 앱 비밀번호
   - 도메인 또는 IP
   - 관리자 비밀번호
4. `docker-compose up -d`로 컨테이너 실행
5. Watchtower 데몬 설치 (자동 업데이트 담당)
6. 방화벽 80/443 자동 오픈
7. 완료 안내 ("브라우저에서 https://... 접속")

**자동 업데이트 흐름:**
```
관리자 새 기능 개발
   ↓
git push → GitHub Actions가 Docker 이미지 빌드
   ↓
Docker Hub에 push (또는 GitHub Container Registry 무료)
   ↓
모든 사용자 서버의 Watchtower가 1시간마다 확인
   ↓
새 이미지 발견 → pull → 컨테이너 재시작 (~1분)
   ↓
사용자는 모르고 새 버전 사용 중
```

| 평가 | 점수 |
|------|------|
| 난이도 | ⭐⭐ (SSH 한 번) |
| 자동화 | ⭐⭐⭐⭐⭐ |
| 비용 | 무료 |
| 안정성 | ⭐⭐⭐⭐ |

---

#### 옵션 B — GitHub Actions + Webhook
- 코드 push → GitHub이 사용자 서버에 알림 → 서버가 받음
- 사용자 서버 IP를 GitHub에 알려줘야 함 (보안 영향)

| 평가 | 점수 |
|------|------|
| 난이도 | ⭐⭐⭐ |
| 자동화 | ⭐⭐⭐⭐⭐ |
| 보안 | ⚠️ |

---

#### 옵션 C — 우리가 SaaS로 호스팅
- 사용자는 그냥 웹 접속만
- ❌ 분산 배포 의도 위배 (각자 Oracle 쓰는 이유 사라짐)

#### 옵션 D — 압축 파일 + GUI 설치
- "다운로드 → 더블클릭"

### 3.4 자동 업데이트 안전 장치

| 안전 장치 | 동작 |
|----------|------|
| 환경변수 백업 | 업데이트 전 `.env`를 `.env.bak.YYYYMMDD`로 자동 백업 |

| GPG 서명 검증 | install.sh, 이미지 모두 서명 검증 |

## 5-A. 결정 항목 초보자 설명 (Q&A)

### A. 이미지 레지스트리 — Docker Hub vs ghcr.io

**비유**: 택배 상하차장 (BlogAuto 프로그램을 보관할 창고)

| 항목 | Docker Hub | ghcr.io |
|------|-----------|---------|
| 운영 주체 | Docker 회사 | GitHub |
| 별도 계정 | 필요 | 불필요 (GitHub 계정 그대로) |
| 다운로드 제한 | 월 200회 | 사실상 무제한 |
| GitHub 통합 | 별도 설정 | 자동 |

**권장**: ⭐ **ghcr.io** — GitHub 한 곳에서 관리, 무제한 무료

---

### B. install.sh 호스팅 — 자체 도메인 vs GitHub Pages

**비유**: 명함 주소 (사용자가 install.sh를 받을 URL)

| 항목 | 자체 도메인 | GitHub Pages |
|------|-----------|--------------|
| URL 예시 | `https://blogauto.com/install.sh` | `https://[user].github.io/.../install.sh` |
| 비용 | 연 1~2만원 | 무료 |
| HTTPS | 별도 설정 | 자동 |
| 설정 시간 | 15분 + DNS | 5분 |

**권장**: ⭐ **GitHub Pages로 시작 → 사용자 늘면 도메인 구입 후 이전**

---

### C. 베타 채널 — 처음부터 분리 vs 사후 추가

**비유**: 신차 출시 (베타 = 시승차, 정식 = 양산)

| 항목 | 처음부터 분리 | 사후 추가 |
|------|-----------|--------|
| 운영 부담 | 2개 채널 관리 | 1개만 관리 |
| 초기(<10명) | 과잉 설계 | 적정 |
| 사용자 30명+ | 도움 됨 | 그때 추가 |

**권장**: ⭐ **처음엔 정식만, 사용자 30명+에서 베타 채널 추가**

## 5-B. 로컬-서버 불일치 회피 ("Works on my machine" 트라우마)

### 원인 (옛 경험에서 6가지)
1. OS 차이 (Windows ↔ Linux)
2. Python 버전 차이
3. 라이브러리 버전 차이
4. 환경변수 누락
5. 파일 경로 차이 (`C:\` ↔ `/home/`)
6. 시간대/locale 차이

### 해결책 = Docker (이미 BlogAuto가 사용 중)

**비유**: 이사 vs 컨테이너 운송
- 옛 방식: 트럭에 짐 그대로 → 깨지거나 분실
- Docker: 컨테이너 박스 → 어디로 가도 그대로

**Docker 이미지에 포함되는 것:**
- ✅ OS 종류, Python 버전, 라이브러리, 환경변수, 경로, 시간대

### 3중 안전장치
| 장치 | 동작 |
|------|------|
| Health Check | 컨테이너 시작 후 자동 진단, 실패 시 재시작 |
| 자동 롤백 | 새 버전 healthcheck 실패 시 이전 버전 복귀 |
| 스테이징 환경(선택) | 리허설 서버 운영 (Oracle 인스턴스 1개 추가) |

### 추가 체크리스트 (사람이 빠뜨릴 수 있는 것)
- `.env.required` 검증 (이미 구현됨)
- 컨테이너 시작 시 자동 `alembic upgrade head`
- 환경변수 `TZ=Asia/Seoul` 고정
- `.env` 권한 600

### 결론
> BlogAuto는 이미 Docker 기반 → 옛 트라우마 가능성 매우 낮음.  
> 추가로 healthcheck + 자동 롤백만 적용하면 거의 완벽.

## 5-C. 데이터 관리 — 본인 승계 + 다른 사용자 빈 상태

### 시나리오 A — 본인 데이터 승계

**방법 1: DB 덤프 + 복원** (표준)
```bash
# 로컬에서
docker-compose exec postgres pg_dump -U blogauto blogauto_v2 > my_data.sql

# Oracle 서버에서
docker-compose exec -T postgres psql -U blogauto blogauto_v2 < my_data.sql
```

**방법 2: 볼륨 통째 복사** (빠름)

**잊기 쉬운 것:**
- `media/blogs/` (템플릿 이미지/폰트)
- `app/static/generated/images/` (생성 이미지)
- `.env` (단, 키 일부는 새로 발급 권장)

### 시나리오 B — 다른 사용자 빈 상태

설치 시 흐름:
```
install.sh 실행 → 빈 PostgreSQL → alembic이 테이블 자동 생성
    → 마법사 "관리자 계정 만들기" → 첫 관리자 1명만 생성 → 빈 상태 시작
```

**보장**: 관리자(개발자)의 모든 데이터(블로그/글/AI 키) 절대 노출 안 됨

### 두 시나리오 동시 지원

```bash
# 일반 사용자 (빈 데이터)
curl -fsSL https://.../install.sh | bash

# 관리자 본인 마이그레이션 (데이터 승계)
curl -fsSL https://.../install.sh | bash -s -- --restore-from=my_data.sql
```

### 권장 워크플로우
| 단계 | 작업 |
|------|------|
| 1 | 로컬 데이터 백업 스크립트(`backup-local.sh`) 작성 |
| 2 | Oracle 서버에 install.sh로 빈 BlogAuto 설치 |
| 3 | 백업 파일 업로드 후 복원 |
| 4 | 다른 사용자에게는 install.sh URL만 공유 |

## 8. 비유로 정리하는 전체 그림

> **BlogAuto = 자동차**  
> **install.sh = "차 키 받아서 시동 거는 방법" 1줄 매뉴얼**  
> **Watchtower = 자동차의 자동 소프트웨어 업데이트 (테슬라처럼)**  
> **인증 시스템 = 차에 나중에 다는 블랙박스 / 도난 방지 장치**  
>
> 자동차(BlogAuto)는 지금 출고하고,  
> 도난 방지 장치(인증)는 나중에 부착해도 차가 굴러가지 않는 게 아니다.
